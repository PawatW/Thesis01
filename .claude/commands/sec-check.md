ตรวจความปลอดภัยของ: **$ARGUMENTS** (ถ้าว่าง = ไฟล์ที่แก้ไปใน session นี้ หรือถามผู้ใช้ว่าจะตรวจส่วนไหน)

## วิธีทำ

1. อ่าน `docs/security-rules.md` (checklist) และ `docs/security-design.md` §2–§5 (trust boundary + contract ของ RPC) ก่อนเสมอ
2. ระบุว่าสิ่งที่ตรวจแตะหมวดไหนบ้าง แล้วไล่เฉพาะหมวดนั้นตามตาราง "เมื่อไหร่ต้องรันอะไร" ท้าย security-rules.md:
   - migration / schema → checklist **C**
   - RPC / Edge Function → checklist **D**
   - หน้าจอหรือ query ฝั่งแอพ → checklist **B**
   - ปิดเฟส → **A–F ทั้งหมด**
3. รันคำสั่งสแกนใน §E-1 ด้วย PowerShell จริง (ข้ามได้ถ้าโฟลเดอร์ `anan/src`, `anan/app` ยังไม่ถูกสร้าง)
4. ถ้ามี migration ใหม่: รัน `npm run test:e2e -- db-invariants` (ชั้น L3) เพื่อพิสูจน์ว่า CHECK/FK/UNIQUE ยังปฏิเสธข้อมูลเสียจริง แล้วไล่ §F-2 ว่า Prisma ไม่ได้กำลังจะลบ constraint ที่เขียนมือไว้
5. สำหรับทุกฟีเจอร์ที่มีการเขียนข้อมูล ให้ถามคำถามชุดนี้กับโค้ดที่ตรวจ:
   - client โกหกฟิลด์ไหนได้บ้าง แล้วเสียหายอย่างไร (โดยเฉพาะเงิน สถานะ สิทธิ์ และ FK ที่ชี้ไปของคนอื่น)
   - ถ้าข้าม UI แล้วยิง REST/RPC ตรงด้วย curl จะโดนปฏิเสธที่ชั้นไหน — ถ้าตอบไม่ได้ = ยังไม่ปลอดภัย
   - ร้านค้า/ผู้ใช้คนอื่นเห็นข้อมูลอะไรเพิ่มขึ้นจากการเปลี่ยนแปลงนี้

## รูปแบบผลลัพธ์ (ภาษาไทย)

- ตารางสรุป: `ข้อ | สถานะ (ผ่าน/ไม่ผ่าน/ไม่เกี่ยว) | หลักฐาน (ไฟล์:บรรทัด)`
- รายการ finding เรียงตามความรุนแรง 🔴 critical / 🟠 high / 🟡 medium พร้อม **สถานการณ์โจมตีที่เป็นรูปธรรม** (ใครยิงอะไร ได้อะไร) และวิธีแก้ที่ชั้นไหน (GRANT / RLS / RPC / trigger / constraint)
- ถ้าไม่พบอะไรเลย: บอกตรง ๆ ว่าผ่าน พร้อมระบุว่าตรวจอะไรไปบ้างและ **ไม่ได้** ตรวจอะไร
- ห้ามรายงานว่าผ่านโดยที่ยังไม่ได้เปิดไฟล์จริง

ถ้าพบ finding ที่แก้ได้ทันทีและอยู่ในขอบเขตของงานนี้ ให้เสนอ patch สั้น ๆ ก่อนถามว่าจะให้แก้เลยไหม (อย่าแก้ schema เองโดยไม่ถาม — ต้องผ่าน migration ใหม่ตามกฎข้อ 4)
