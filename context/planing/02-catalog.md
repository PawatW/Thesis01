# Feature 02: Catalog — เลือกดูสินค้าตามหมวด

> เฟส: 2 | ฝั่ง: Buyer | สถานะ: ✅ เสร็จ (Phase 2) — คะแนนรีวิวบนการ์ดเพิ่มใน Phase 4.5 | Workflows: [W03](../workflows/w03-browse-compare.md)

## ทำอะไรได้

- หน้าแรก: หมวดทั้งหมด + สินค้าแนะนำ
- ดูสินค้าตามหมวด (10 หมวดตาม proposal), ค้นหาจากชื่อ, เรียงราคา/ความนิยม
- การ์ดสินค้า: รูป, ชื่อ, ร้าน, **ราคาต่อรอบต่ำสุด**, % ส่วนลดเทียบซื้อครั้งเดียว, รอบส่งที่มี, **คะแนนรีวิว** ([17](17-reviews.md)), ปุ่ม "เทียบ"

## หน้าจอ & Routes

| Route | หน้าจอ |
|---|---|
| `(buyer)/index.tsx` | หน้าแรก — แถบหมวดแบบ **เช็คบ็อกซ์ติ๊กได้หลายหมวด** (กรองกริดในหน้านี้เลย ไม่เด้งไปหน้าหมวด) + grid สินค้าแนะนำ + ช่องค้นหา |
| `(buyer)/category/[id].tsx` | สินค้าในหมวด — grid + sort + ปุ่มเทียบ + แถบถาดเทียบลอยล่าง |
| `app/search.tsx` | หน้าผลค้นหารวม — รับ `?q=` จากช่องค้นหาหน้าแรก · แถบ "ร้านค้าที่เกี่ยวข้อง" (สูงสุด 3 การ์ด, ซ่อนทั้งแถบถ้าไม่มีร้านตรงคำค้น) + sort chips + กริดสินค้า · วางนอกกลุ่ม `(buyer)` เหมือน `compare.tsx` เพราะเป็นหน้าที่ push ทับ ไม่ใช่แท็บ |

## Components หลัก

- `ProductCard` — ใช้ทั้งหน้าแรก/หมวด/ร้านค้า; props: product + onCompareToggle
- `CategoryChip`, `SearchBar`, `SortSelect` (ราคาต่ำ-สูง / ยอดนิยม)
- `CompareTrayBar` — แถบลอยล่างเมื่อถาดเทียบมีของ (state จาก feature 04)

## Data & Queries (API)

| Endpoint | ใช้ที่ |
|---|---|
| `GET /catalog/categories` | แถบหมวดบนหน้าแรก |
| `GET /catalog/products?category=&categories=&q=&sort=&limit=` | กริดสินค้า · ค้นหา · เรียงลำดับ (public — ไม่ต้องล็อกอิน) · `categories=1,8` = กรองหลายหมวดพร้อมกัน (ยูเนียน) ใช้ที่แถบเช็คบ็อกซ์หน้าแรก |
| `GET /catalog/shops/:id` | หน้าร้านสาธารณะ (กดจากชื่อร้านบนหน้าสินค้า) |
| `GET /catalog/shops?q=&limit=` | แถบ "ร้านค้าที่เกี่ยวข้อง" บนหน้า `/search` — ค้นชื่อร้านด้วย `q`, จำกัดจำนวนด้วย `limit` (default 6, สูงสุด 20), ไม่ส่ง `q` = คืนร้านที่มองเห็นได้ทั้งหมดเรียงตามจำนวนสินค้า |

- **`VISIBLE_PRODUCT` คือนิยามเดียวของ "สินค้าที่ลูกค้าเห็นได้"** (`is_active` + ร้านเปิด + ทั้งสินค้าและร้านไม่ถูกระงับ) ใช้ร่วมกันทั้ง catalog · checkout · หน้าร้าน — ลืมใส่ที่ไหนสักที่แล้วของที่ถูกระงับจะโผล่ทันที จึงห้ามเขียน where เองซ้ำ
- **ตัวเลข aggregate มาพร้อมสินค้าในคำขอเดียว** — `activeSubscribers`, `rating`, `reviewCount` คำนวณฝั่ง API (ของเดิมต้องยิง 3 request แล้ว join กันเองในเครื่องผู้ใช้) · เป็น count/avg ล้วน ไม่มีข้อมูลรายคนออกไป
- ฝั่งแอปคำนวณต่อการ์ดจากข้อมูลที่ได้มา: `cheapestPlan()` · `discountPercent()` · `pricePerUnit()` — สูตรทั้งหมดอยู่ที่ `anan/src/features/catalog/api.ts` ที่เดียว (ใช้ร่วมกับ features 03/04/11)
- สินค้าแนะนำหน้าแรก = เรียงตามจำนวนสมาชิกที่ยังใช้งานอยู่
- **หมวดบนหน้าแรกเป็นเช็คบ็อกซ์ ไม่ใช่ลิงก์** (2026-08-30) — ติ๊กแล้วกรองกริดในหน้าเดิม ยังไม่ติ๊ก = แสดง "คนสมัครเยอะที่สุด" ตามเดิม
  - เหตุผล: ผู้ซื้อของใช้ประจำคิดเป็นชุด ("ยาสีฟัน + แชมพู") การบังคับให้เข้าทีละหมวดทำให้เทียบข้ามหมวดไม่ได้ · หน้า `/category/[id]` ยังอยู่ (เข้าจาก URL / ที่อื่นได้)
  - กรองด้วยการยิง API ใหม่ทุกครั้ง ไม่กรอง array ที่โหลดมาแล้วในเครื่อง เพราะหน้าแรกโหลดมาแค่ 8 ชิ้นแรก — กรองในเครื่องจะได้ผลลัพธ์ที่ "หายไป" เงียบ ๆ
  - `categories` มาก่อน `category` เมื่อส่งมาทั้งคู่ (ไม่ AND ทับกันจนได้ผลว่าง) · ค่าที่ไม่ใช่จำนวนเต็มบวก → 400 ที่ DTO ไม่ไหลไป Prisma · เพดาน 30 หมวดต่อคำขอ
- **`q` ของ `GET /catalog/products` ตอนนี้ match ทั้งชื่อสินค้า OR ชื่อร้าน** (`where.OR = [{ name contains q }, { shop.name contains q }]`) — เพิ่มเพื่อรองรับหน้า `/search`: พิมพ์ชื่อร้านแล้วต้องเห็นสินค้าของร้านนั้นในกริดด้วย ไม่ใช่แค่ชื่อสินค้าตรงตัว · `shop: VISIBLE_SHOP` ยังถูก AND ไว้ที่ระดับบนสุดเสมอ ร้านที่ถูกระงับจึงไม่หลุดออกมาทาง OR ฝั่งนี้

### ทำไมไม่มี "ผู้ติดตาม / อัตราตอบแชท / ป้าย Mall" แบบ Shopee บนการ์ดร้าน

การ์ดร้าน (`ShopCard`) เอา layout มาจาก Shopee (โลโก้ซ้าย / ชื่อ+คำอธิบาย / สถิติขวา) แต่**ตัวเลขที่โชว์เลือกเฉพาะสิ่งที่ระบบมีข้อมูลจริง**:

- **ผู้ติดตาม (follow), อัตราตอบแชท (chat), ป้าย "Mall"/ผู้ขายยืนยันตัวตน, เลขทะเบียนนิติบุคคล → ไม่ทำ** เพราะระบบนี้ไม่มี follow/chat/merchant-tier เลย (ไม่ใช่แค่ยังไม่ทำ UI — ไม่มีตารางเก็บข้อมูลพวกนี้ด้วย) การใส่ตัวเลขที่ไม่มีแหล่งข้อมูลจริงรองรับขัดกับหลักการเดียวกับกฎ "เงิน/สิทธิ์ห้ามมาจาก client" (CLAUDE.md ข้อ 7) — คือห้ามโชว์สิ่งที่ไม่ได้มาจาก DB จริง
- **ใช้ `activeSubscribers` (จำนวนสมาชิกที่สมัครอยู่ตอนนี้) แทน "ผู้ติดตาม"** เพราะ (1) เป็นตัวเลขที่มีอยู่แล้วในระบบ ไม่ต้องเพิ่มตาราง/ฟีเจอร์ใหม่ (2) เข้ากับโมเดล subscription commerce ของแพลตฟอร์มนี้มากกว่า — สมาชิกที่สมัครอยู่คือคนที่ตัดเงินจริงประจำรอบ ไม่ใช่แค่คนกดติดตามเฉย ๆ แบบ e-commerce ทั่วไป จึงเป็นสัญญาณความน่าเชื่อถือของร้านที่ตรงกับธุรกิจจริงกว่า (3) เป็น aggregate ล้วน (`count`) ไม่มี `buyerId`/ข้อมูลรายคนหลุดออกมา ตรงตามกฎข้อ 7 ที่ว่า "ร้านค้าเห็นข้อมูลผู้ซื้อเท่าที่ต้องส่งของ" — การ์ดร้านที่ผู้ซื้อคนอื่นเห็นยิ่งต้องเข้มกว่านั้นอีก (ไม่มีข้อมูลผู้ซื้อออกไปเลยสักตัว)

### ข้อจำกัด: ค้นหาด้วย `ILIKE '%q%'` ยังไม่มี index (เขียนลงเล่ม บท "ข้อจำกัดของระบบ" ได้)

ทั้ง `GET /catalog/products?q=` และ `GET /catalog/shops?q=` ใช้ Prisma `contains` (แปลงเป็น `ILIKE '%q%'` ของ Postgres) ซึ่ง**สแกนทั้งตาราง (Seq Scan) ทุกครั้งที่ค้น** เพราะ B-tree index มาตรฐานช่วย pattern ที่ขึ้นต้นด้วย `%` ไม่ได้ — ต้องมี extension `pg_trgm` + GIN index (เช่น `CREATE INDEX ... USING gin (name gin_trgm_ops)`) ค้นถึงจะเร็วขึ้นอย่างมีนัยสำคัญเมื่อข้อมูลโต

**ตัดสินใจไม่ทำรอบนี้** เพราะข้อมูลระดับ demo (สินค้า/ร้านหลักสิบถึงหลักร้อยแถว) เร็วพอโดยไม่ต้องมี index อยู่แล้ว ส่วนต้นทุนของ `pg_trgm` (ต้องมีสิทธิ์ `CREATE EXTENSION` ซึ่ง managed Postgres บางเจ้าไม่ให้สิทธิ์นี้) ไม่คุ้มกับข้อมูลระดับ prototype — ถ้าต้อง scale ขึ้นจริง (ผู้ใช้/สินค้าหลักหมื่นแถว) แนะนำเพิ่ม `pg_trgm` GIN index ก่อน หรือย้ายไปใช้ full-text search แยกต่างหาก (Postgres `tsvector`, Elasticsearch, Meilisearch) ถ้า workload การค้นหาหนักขึ้นเรื่อย ๆ

## Validation & Edge cases

- หมวดว่าง → empty state "ยังไม่มีสินค้าในหมวดนี้"
- ร้านถูกระงับโดย admin ([14](14-admin.md)) หรือปิดร้านเอง → สินค้าทั้งร้านหายให้อัตโนมัติ เพราะทุก query ของ catalog ผ่าน `VISIBLE_PRODUCT` ตัวเดียวกัน · เปิด URL ของสินค้านั้นตรง ๆ ก็ได้ 404 เหมือนไม่มีอยู่ (ไม่บอกว่า "มีแต่โดนแบน")
- สินค้าที่ทุกแผน inactive → ไม่แสดงปุ่ม subscribe บนการ์ด (แสดง "ปิดรับชั่วคราว")
- รูปเสีย/ไม่มี → placeholder สีหมวด
- ค้นหา: debounce 300ms, ผลว่าง → "ไม่พบ 'คำค้น'"
- หน้า `/search`: debounce 300ms เดียวกัน · ไม่พบทั้งร้านและสินค้าที่ตรงคำค้น → empty state เดียว (`#search-empty`) ไม่ใช่สองก้อนซ้อนกัน · มีร้านแต่ไม่มีสินค้า (หรือกลับกัน) → โชว์เฉพาะแถบที่มีผล ไม่ใช่ empty state
- grid: มือถือ 2 คอลัมน์ / web ≥3 คอลัมน์ (responsive — กฎ CLAUDE.md ข้อ 3)

## Acceptance Criteria

- [ ] เปิดหน้าแรกเห็น 10 หมวด + สินค้าแนะนำเรียงตาม subscriber
- [ ] ติ๊กหมวดบนหน้าแรก (หลายหมวดได้) → กริดในหน้าเดิมเหลือเฉพาะสินค้าของหมวดที่ติ๊ก · ล้างตัวกรองแล้วกลับเป็น "คนสมัครเยอะที่สุด"
- [ ] เข้าหมวด → เห็นเฉพาะสินค้า active หมวดนั้น การ์ดโชว์ราคาต่อรอบต่ำสุด + ส่วนลดถูกต้อง
- [ ] ค้นหา/เรียงลำดับทำงาน, ผลว่างมี empty state
- [ ] แสดงผลถูกทั้ง mobile (2 คอลัมน์) และ web (≥3 คอลัมน์)
- [x] ค้นจากช่องค้นหาหน้าแรกแล้วเจอร้าน (การ์ดร้านขึ้นในหน้า `/search`)
- [x] กดการ์ดร้านในหน้าค้นหา เข้าหน้าร้าน (`shop/[id].tsx`) ได้
- [x] ค้นด้วยชื่อร้านแล้วเจอสินค้าของร้านนั้นในกริด (ไม่ใช่แค่ชื่อสินค้าตรงตัว)
- [x] ร้านที่ถูกระงับ / ปิดเอง / ไม่มีสินค้าขาย ไม่โผล่ในผลค้นหา ทั้งแถบร้านและกริดสินค้า
