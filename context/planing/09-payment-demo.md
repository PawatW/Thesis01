# Feature 09: Payment (Demo) — ระบบจ่ายเงินจำลอง

> เฟส: 2 (พื้นฐาน), 5 (โพลิช), 7.1 (ฟอร์มบัตรแบบของจริง 2026-08-20) | ฝั่ง: Buyer | สถานะ: **เสร็จแล้ว** | Workflows: [W04](../workflows/w04-subscribe-checkout.md), [W06](../workflows/w06-recurring-cycle.md)
> **กฎเหล็ก (CLAUDE.md ข้อ 1): การตัดเงินจำลอง 100% — ห้ามเชื่อม payment gateway จริงทุกกรณี**
>
> **ขอบเขตของคำว่า "จำลอง" (ปรับ 2026-08-20):** จำลองเฉพาะ *การตัดเงิน* — ส่วน *การผูกบัตร*
> ทำงานเหมือนของจริงทุกขั้น (Luhn · อ่านเครือข่ายจาก BIN · วันหมดอายุ · CVV · กันบัตรซ้ำ)
> และหน้าจอผูกบัตรไม่มีคำว่า "จำลอง/สมมติ" เพราะทุกอย่างที่บันทึกกับด่านที่ผ่านเป็นของจริง

## ทำอะไรได้

- **ผูกบัตร** ด้วยฟอร์มแบบเดียวกับร้านค้าออนไลน์จริง: เลขบัตร (จัดกลุ่ม 4-4-4-4 · Amex 4-6-5) · วันหมดอายุ ดด/ปป · CVV · ชื่อบนบัตร
  พร้อมหน้าบัตรตัวอย่างที่ขยับตามที่พิมพ์ · ระบบเก็บ **เครือข่าย · last4 · เดือน/ปีหมดอายุ · ชื่อบนบัตร** เท่านั้น
  (ชุดเดียวกับที่ผู้ให้บริการจริงเก็บหลัง tokenization — **ไม่มีเลขบัตรเต็ม ไม่มี CVV** ที่ไหนเลย)
- ตัดเงินจำลองอัตโนมัติ: รอบแรกตอน checkout, รอบถัดไปโดย engine → แถว `payments` (paid)
- **คืนเงินจำลอง** เมื่อร้านยกเลิกออเดอร์ → `payments.status = 'refunded'` + `refunded_at` ([feature 15](15-order-exceptions.md)) — เกิดในทรานแซกชันเดียวกับการยกเลิกเสมอ
- ประวัติการจ่าย + ใบเสร็จจำลองต่อออเดอร์
- **UI ทุกจุดที่แตะ*ยอดเงิน*ติดป้าย "DEMO — ไม่มีการตัดเงินจริง"** (หน้าจอผูกบัตรไม่ติด — ดูขอบเขตด้านบน)
- (เฟส 5) โหมดจำลอง "ตัดเงินไม่ผ่าน" เพื่อ demo flow retry ต่อกรรมการ

## สถาปัตยกรรม: PaymentProvider interface

```ts
// anan-api/src/payments/payment.provider.ts — จุดออกแบบสำคัญที่สุดของ feature นี้
export abstract class PaymentProvider {
  abstract charge(input: {
    orderId: string;
    amount: number;
    card: { id: string; last4: string };
  }): Promise<{ status: 'paid' | 'failed'; failureReason: string | null }>;
}
// implementation เดียวในโปรเจกต์: DemoPaymentProvider (ผูกไว้ที่ PaymentsModule แบบ @Global)
//  - ไม่ต่อออกนอกเครื่องแม้แต่บรรทัดเดียว และไม่เคยเห็นเลขบัตรเต็ม (ระบบเก็บแค่ last4)
//  - **บัตรที่ลงท้าย 0000 = ถูกปฏิเสธเสมอ** (`DEMO_DECLINE_LAST4`) นอกนั้นผ่านหมด
// ห้ามมี StripeProvider/OmiseProvider ในโค้ดจริง — เขียนถึงได้เฉพาะในเล่ม
```

- **ทั้ง checkout · engine · การจ่ายซ้ำ เรียกผ่าน `PaymentProvider` ตัวเดียวกัน** — ไม่มีที่ไหนในระบบเขียน `status: 'paid'` เองอีกแล้ว
- ทำไมเป็น `abstract class` ไม่ใช่ `interface`: Nest ต้องการค่า runtime เป็น DI token ส่วน `interface` ของ TypeScript หายไปตอน compile
- **ทำไมเลือก "บัตรลงท้าย 0000" แทน `DEMO_FAIL_RATE` แบบสุ่ม:** การนำเสนอต้องทำซ้ำได้ ตอนซ้อมกับตอนขึ้นเวทีต้องเกิดเหมือนกัน และกรรมการต้องเห็นจากหน้าจอว่าอะไรเป็นตัวกำหนด — เป็นแนวเดียวกับบัตรทดสอบของ gateway จริง

## Components หลัก

- `features/payment/card.ts` — ตรรกะบัตรทั้งหมดฝั่งเครื่องผู้ใช้: Luhn · ตาราง BIN → เครือข่าย · จัดรูปเลข/วันหมดอายุ ·
  `toCardPayload()` คือ **จุดเดียวที่เลขบัตรเต็มถูกทิ้ง** ก่อนยิง API
- `features/payment/CardForm.tsx` — ฟอร์มผูกบัตร ใช้ร่วมกันระหว่างหน้า "บัตรของฉัน" กับหน้าจ่ายเงิน (มี re-entrancy guard ตาม C-9)
- `features/payment/CardFace.tsx` — หน้าบัตรตามสัดส่วน ISO/IEC 7810 ID-1 · ใช้ทั้งในรายการบัตรและเป็นตัวอย่างสดระหว่างพิมพ์
- `DemoBadge` — component กลาง ใช้ทุกจุดที่มีตัวเลขเงิน (checkout, ใบเสร็จ, dashboard ร้าน)
- `ReceiptModal` — เลขที่ใบเสร็จจำลอง, รายการ, ยอด, วันเวลา, ป้าย DEMO ใหญ่ๆ

## Data & Queries (API)

| Endpoint | ใช้ที่ |
|---|---|
| `POST /me/payment-methods` | ผูกบัตร — DTO รับแค่ `brand` · `last4` · `expMonth` · `expYear` · `holderName` (ไม่มีเลขบัตรเต็ม ไม่มี CVV) |
| `GET /me/payment-methods` · `DELETE /me/payment-methods/:id` | รายการบัตร / ลบ (แก้ไม่ได้) |
| `POST /orders/:id/retry-payment` | จ่ายรอบที่ถูกปฏิเสธอีกครั้ง — **ไม่มี body เลย** ยอดกับบัตรมาจากออเดอร์ในฐานข้อมูล |
| `GET /orders/:id` | ใบเสร็จอ่านจาก `paymentStatus` / `paidAt` / `receiptNo` ของ response เดิม |

- **ไม่มี endpoint ไหนให้ client เขียนตาราง `payments`** — เขียนโดย checkout · engine · retry เท่านั้น (ถ้า client insert `status:'paid'` เองได้ = ได้ของฟรี · [S-02](../../docs/security-design.md))
- `unique (order_id)` บน `payments` = กันตัดเงินซ้ำที่ระดับ DB (คู่กับ UQ ของ orders) และ CHECK `payments_lifecycle` บังคับว่าแต่ละสถานะต้องมีเวลากำกับให้ตรง
- **เลขที่ใบเสร็จไม่ได้เก็บเป็นคอลัมน์** — คำนวณจาก id ของออเดอร์ (`RC-XXXXXXXX`) เพราะใบเสร็จ 1 ใบต่อออเดอร์อยู่แล้ว การมี sequence กลางที่ต้องล็อกทุกครั้งจึงเป็นหนี้เปล่า ๆ

## Validation & Edge cases

- เลขบัตร: ความยาวตามเครือข่าย (Amex 15 · UnionPay 16–19 · ที่เหลือ 16) **และต้องผ่าน Luhn** — ด่านนี้อยู่ฝั่งหน้าจอเพราะ API ไม่เคยเห็นเลขเต็ม
- วันหมดอายุ: หมดอายุ "สิ้นเดือน" ที่พิมพ์บนบัตร · ตรวจซ้ำที่ service (`CARD_EXPIRED` 400) ด้วยปฏิทิน Asia/Bangkok และมี CHECK ช่วง 1–12 / 2000–2100 ที่ DB
- **ผูกบัตรใบเดิมซ้ำไม่ได้** — UNIQUE `(user_id, last4, exp_month, exp_year)` → 409 `CARD_ALREADY_ADDED`
  (ของจริงกันด้วย fingerprint ของเลขบัตร ที่นี่ไม่มีเลขเต็มให้ hash จึงใช้ชุดที่เก็บไว้จริงแทน)
- **เครือข่ายบัตรรับจาก client ได้** เพราะเป็นป้ายกำกับสำหรับแสดงผลของบัตรตัวเอง ไม่ได้ใช้ตัดสินเงิน/สิทธิ์/สถานะ (กฎข้อ 7)
- DB มี CHECK `last4 ~ '^[0-9]{4}$'` — ถึงโค้ดพลาดส่งเลขเต็มมาก็ insert ไม่ผ่าน
- CVV ถูกตรวจความยาว (3 หลัก · Amex 4) แล้ว **ทิ้งที่หน้าจอ** — ไม่ถูกส่งขึ้น API และไม่มีคอลัมน์รองรับ เหมือนระบบจริง
- ลบบัตรที่ subscription ใช้อยู่ → FK restrict บล็อก → "บัตรนี้ผูกกับ subscription อยู่ — เปลี่ยนบัตรใน subscription ก่อน"
- ผู้ใช้ยังไม่มีบัตรตอน checkout → เพิ่ม inline (W04 A2)
- ตรวจสอบ: ห้ามมีเลขบัตรเต็มใน state ที่ persist, log, หรือ network call ใดๆ
- **รอบแรกจ่ายไม่ผ่าน (checkout) → rollback ทั้งก้อน** ไม่เหลือ subscription/order/payment ค้างเลย (ผู้ซื้อเปลี่ยนบัตรแล้วสมัครใหม่)
- **รอบถัดไปจ่ายไม่ผ่าน (engine) → ออเดอร์ยังอยู่** พร้อม `payments.status = 'failed'` ให้ผู้ซื้อกดจ่ายซ้ำ · `next_order_date` เลื่อนตามปกติ (รอบนั้นเกิดขึ้นจริงแล้ว การไม่เลื่อนจะทำให้รายการค้างอยู่ที่รอบเดิมตลอดไป)
- **ร้านไม่เห็นออเดอร์ที่ยังจ่ายไม่สำเร็จเลย** — ทั้งในรายการ ในตัวนับ dashboard และยิง `advance` ตรงก็ได้ 404 (ไม่งั้นร้านจัดของให้รอบที่อาจไม่มีวันได้เงิน)
- จ่ายซ้ำสำเร็จ → ร้านได้ notification ตอนนั้น (engine ไม่ได้แจ้งไว้ตอนออเดอร์เกิด เพราะยังไม่ได้เงิน)
- กดจ่ายซ้ำบนรอบที่จ่ายไปแล้ว → 409 · บนออเดอร์ที่ถูกยกเลิกแล้ว → 409 (ไม่ตัดเงินซ้ำ)

## Acceptance Criteria

- [x] ผูกบัตร → DB มีแค่ brand + last4 + วันหมดอายุ (ตรวจตารางจริง) และไม่มีเลขเต็ม/CVV ใน storage/log (**TC-022**, **TC-084**)
- [x] เลขบัตรที่ checksum ไม่ผ่าน / บัตรหมดอายุ ถูกปฏิเสธก่อนยิง API (**TC-023**, **TC-091**)
- [x] ผูกบัตรใบเดิมซ้ำ → 409 และ DB มีใบเดียว (**TC-092** + e2e API)
- [x] checkout + engine สร้าง payments ผูก order ถูกใบ — และทั้งคู่เรียกผ่าน `PaymentProvider` ตัวเดียวกัน
- [x] ใบเสร็จเปิดจากหน้าออเดอร์ได้ ยอดตรง เลขที่คงที่ (**TC-073** เทียบกับยอดใน DB)
- [x] ป้าย DEMO ปรากฏ: checkout, ใบเสร็จ, รายการออเดอร์ทั้งสองฝั่ง, dashboard ร้าน
- [x] ค้นทั้ง codebase ไม่มี import จาก stripe/omise/2c2p (สแกน F-1 ได้ 0 แถว)
- [x] **ไม่มี endpoint ให้ client เขียน `payments` เลย** — สถานะการจ่ายเปลี่ยนได้จาก checkout · engine · `retry-payment` เท่านั้น
- [x] บัตรที่ถูกปฏิเสธตอนสมัคร → 402 และไม่เหลือข้อมูลค้าง (**TC-071** + e2e API)
- [x] รอบที่ตัดเงินไม่ผ่าน → ร้านมองไม่เห็น · ผู้ซื้อจ่ายซ้ำแล้วร้านถึงเห็น (**TC-072**)
