# Feature 14: Admin — ดูแลแพลตฟอร์ม (minimal)

> เฟส: 6 | ฝั่ง: Admin | สถานะ: **เสร็จแล้ว** (2026-08-19 · เพิ่มตั้งค่าเมล + log ระบบ 2026-08-22) ยกเว้นปุ่ม reset demo | Workflows: [W10](../workflows/w10-admin.md)
> ตัดสินใจเพิ่ม 2026-07-12 — ตอบคำถามกรรมการ "แพลตฟอร์มนี้ใครดูแล" | **minimal โดยตั้งใจ: เดิม 4 หน้า · เพิ่มเป็น 6 หน้าเมื่อ 2026-08-22 ตามที่ผู้ใช้สั่ง**

## ทำอะไรได้

- **Dashboard ภาพรวม:** ผู้ใช้/ร้าน/สินค้า/subscription active/ออเดอร์วันนี้/MRR รวม (จำลอง)/ยกเลิกเดือนนี้
- **จัดการหมวดสินค้า:** เพิ่ม/แก้ชื่อ-ไอคอน-ลำดับ/ลบ (เดิมทำได้แค่ seed)
- **Moderation:** ค้นหาร้าน/สินค้า → ระงับ/คืน + **คิวเคสปัญหาจากผู้ซื้อ + อัตรายกเลิกออเดอร์ต่อร้าน** ([16](16-delivery-confirmation.md)/[15](15-order-exceptions.md)) — สัญญาณที่ใช้ตัดสินใจว่าควรระงับร้านไหน
- **ควบคุม engine (ย้ายมาจากหน้า dev):** Run now, time-travel (`run_date` จำลอง), ดู `engine_runs`, reset demo data
- **ตั้งค่าเมล (เพิ่ม 2026-08-22):** เปิด "โหมด DEV" ให้อีเมลทุกฉบับของระบบไปเข้ากล่องเดียวแทนผู้รับจริง + แก้ host/port/ผู้ส่งของ SMTP ได้ (ชื่อผู้ใช้/รหัสผ่านยังอยู่ `.env` เท่านั้น)
- **log ระบบ (เพิ่ม 2026-08-22):** 2 แท็บ — การกระทำในระบบ (`audit_logs`) กับ อีเมลที่ส่งออก (`email_logs`)
- `is_admin` ตั้งผ่าน seed/SQL เท่านั้น — **ไม่มี UI สร้าง admin**

- `AdminGuard` (ใน _layout) — เช็ค profile.is_admin จาก AuthProvider
- `StatCard` — reuse จาก feature 10 + `DemoBadge` บนตัวเลขเงิน

## Data & Queries (API)

| Endpoint | ใช้ที่ |
|---|---|
| `GET /admin/stats` | dashboard — aggregate ล้วน 9 ตัวเลข (ไม่มีแถวของผู้ใช้คนไหนเลย) |
| `GET/POST/PATCH/DELETE /admin/categories` | จัดการหมวด — ทุกแถวพก `productCount` มาด้วย |
| `GET /admin/shops?q=&filter=` · `GET /admin/products?q=` | moderation — พร้อมสัญญาณคุณภาพ (สมาชิก · เคสค้าง · ยกเลิก 30 วัน) |
| `POST /admin/shops/:id/suspension` · `POST /admin/products/:id/suspension` | ระงับ/คืนสถานะ (`{ suspend, reason }`) → คืนจำนวน subscription ที่กระทบ |
| `GET /admin/issues?status=open\|closed` | คิวเคสปัญหาทั้งแพลตฟอร์ม เรียงเคสที่ค้างนานที่สุดก่อน |
| `POST /admin/engine/run` · `GET /admin/engine/runs` | ควบคุม engine (มีมาตั้งแต่ Phase 3) |
| `GET/PUT /admin/mail-settings` | ตั้งค่าเมล — `PUT` ส่งค่าทั้งชุดเสมอ (ไม่ใช่ PATCH) เพราะ "ปิดโหมด" กับ "ไม่ได้แตะโหมด" ต้องแยกกันออก |
| `GET /admin/logs/audit?page=&action=` · `GET /admin/logs/email?page=&status=` | log ระบบ — 50 แถว/หน้า · เพดานหน้าที่ 200 · **ไม่มี DELETE** |

### ตั้งค่าเมล + log ระบบ (เพิ่ม 2026-08-22)

- **ค่าตั้งค่าอยู่ในตาราง `mail_settings` แถวเดียว** (CHECK บังคับ `id = 1`) — เก็บใน DB ไม่ใช่ `.env` เพราะต้องสลับได้ระหว่างซ้อมเดโม่โดยไม่รีสตาร์ต API · ช่องที่เว้นว่าง = "ใช้ค่าจาก `.env` ตามเดิม"
- **`SMTP_USER` / `SMTP_PASS` ไม่มีในหน้าจอและไม่มีใน DTO** — เป็น credential จริง อยู่ `.env` เท่านั้น (กฎข้อ 7) · เทสยิง `smtpPass` มากับ body แล้วต้องได้ 400
- **★ `host`/`port`/`secure` ของ SMTP ก็แก้ได้เฉพาะบนเครื่องที่อนุญาตโหมด DEV เหมือนกัน ★** (403 `SMTP_TARGET_LOCKED`) — บน production เซิร์ฟเวอร์เมลเป็นค่าของการ deploy ไม่ใช่ของหน้าเว็บ · `mailFrom` ยังแก้ได้เสมอเพราะเป็นแค่ชื่อผู้ส่ง
- **★ เปิดโหมด DEV ได้เฉพาะเมื่อเครื่องอนุญาต ★** `MAIL_UAT_MODE_AVAILABLE=true` **และ** `NODE_ENV != production` — ด่านอยู่ที่ `SettingsService` ไม่ใช่ที่ปุ่ม · เหตุผล: เปิดโหมดนี้บน production = ผู้ใช้จริงไม่ได้รับลิงก์กู้บัญชีอีกเลย และคนที่ถือปลายทางได้ลิงก์ของ **ทุกคน** แทน (account takeover ทั้งระบบในคลิกเดียว) บัญชี admin ที่ถูกยึดจึงต้องทำไม่ได้
- **อีเมลทุกฉบับผ่าน `MailService.send()` ที่เดียว** — การเปลี่ยนเส้นทางกับการบันทึก log อยู่ตรงนั้น · feature ใหม่ที่เรียก nodemailer เองจะหลุดทั้งสองอย่าง
- **เมลที่ถูกเปลี่ยนเส้นทางมีแถบบอกผู้รับตัวจริง** ทั้งในเนื้อเมลและในหัวเรื่อง (`[DEV → someone@x.com] …`) — กล่อง QA ที่รับของทุกคนรวมกันต้องแยกออกว่าฉบับไหนของใคร
- **`email_logs` ห้ามเก็บเนื้อเมล** — เนื้อเมลรีเซ็ตรหัสผ่านมีลิงก์ที่ตั้งรหัสผ่านของบัญชีได้ · เก็บแค่ปลายทาง + ผลลัพธ์ · CHECK `email_logs_redirect_consistent` ทำให้ธง `redirected` โกหกไม่ได้
- **`audit_logs` เขียนอย่างเดียว** — ไม่มี endpoint แก้/ลบ · การกระทำกับ log อยู่ในทรานแซกชันเดียวกัน (ยกเว้น engine กับการรีเซ็ตรหัสผ่านที่บันทึกหลังงานจบ พร้อมเหตุผลในโค้ด) · `summary` ถูกสรุปเป็นข้อความไทยตั้งแต่ตอนเขียน เพราะของที่ถูกอ้างถึงอาจถูกลบไปแล้วตอนอ่าน

- **ทุก endpoint อยู่ใต้ `@Roles('admin')` ที่ระดับ class** — endpoint ใหม่ในไฟล์เดียวกันจึงถูกปิดโดยปริยาย ไม่ต้องพึ่งว่าคนเขียนจะจำใส่ทีละเมธอด
- **ไม่มี DTO ตัวไหนมีฟิลด์ `suspendedAt` / `isAdmin`** — เวลาที่ระงับเป็นของ server เสมอ และสิทธิ์ admin ตั้งผ่าน seed/SQL เท่านั้น
- **การระงับไม่ใช่การแก้ `is_active`** — `is_active` เป็นของเจ้าของร้าน (เขาปลดเองได้) ส่วน `suspended_at` แก้ได้จาก endpoint นี้ที่เดียว
- ลบหมวด: **ปล่อยให้ FK เป็นคนบล็อก** แล้วค่อยนับจำนวนสินค้าไปบอกผู้ใช้ — การนับก่อนลบมีช่องให้สินค้าใหม่แทรกเข้ามาระหว่างสองคำสั่ง

## Validation & Edge cases

- non-admin เข้า route ตรงๆ → redirect + ฝั่ง DB ก็โดน RLS/RPC ปฏิเสธอยู่ดี (ป้องกัน 2 ชั้น — ทดสอบทั้งคู่)
- **ระงับร้านแล้วสินค้าหายจาก catalog โดยอัตโนมัติ** — RLS ของ `products`/`product_plans` เช็ค `shop.suspended_at is null` ให้แล้ว (ไม่ต้องพึ่ง `shops!inner` ฝั่ง client แต่ยังใส่ไว้ได้เพื่อความชัดเจนของ query)
- **ระงับร้าน/สินค้า = แช่แข็ง subscription ทั้งหมดของร้านนั้น** (`status='paused'`, `paused_reason='shop_suspended'`) + แจ้งผู้ซื้อ — แก้เมื่อ 2026-07-25 เพราะของเดิม "ไม่แตะ subscriber" แปลว่าแพลตฟอร์มยังตัดเงินเข้าร้านที่ตัวเองสั่งระงับ; ปลดระงับแล้วระบบ resume ให้อัตโนมัติ (`next_order_date = max(เดิม, พรุ่งนี้)`)
- ผู้ซื้อ **resume subscription ที่ถูกแช่แข็งเองไม่ได้** จนกว่าร้านจะถูกปลดระงับ (บังคับด้วย trigger ระดับ DB)
- ออเดอร์ที่ค้างส่งอยู่ก่อนถูกระงับยังเดินต่อจนจบ (ผู้ซื้อจ่ายไปแล้ว)
- ลบหมวดที่มีสินค้า → FK restrict บล็อก → "ย้ายสินค้าออกจากหมวดก่อน" (จำนวนสินค้าโชว์ข้างชื่อหมวด)
- admin ที่เป็น seller/buyer ด้วย → สลับได้ 3 โหมด (toggle ในโปรไฟล์แสดงตามสิทธิ์)
- reset demo ต้อง confirm พิมพ์ "RESET" (กันมือลั่นตอนซ้อมเดโม่)

- [x] บัญชีธรรมดาเข้า `(admin)/` ไม่ได้ **และ** ยิง API ตรงได้ 403 ทุกเส้น (**TC-075** + e2e API)
- [x] ตัวเลข dashboard ตรงกับข้อมูลจริง — **TC-076** เทียบกับ `count(*)` ของ DB ตรง ๆ
- [x] เพิ่ม/แก้/ลบหมวด → หน้า catalog ฝั่ง buyer สะท้อนทันที (**TC-078**) · ลบหมวดที่มีสินค้าถูก FK บล็อกพร้อมบอกจำนวน
- [x] ระงับร้าน → สินค้าหายจาก catalog + subscription ทั้งหมดถูก pause (`paused_reason='shop_suspended'`) + แจ้งเตือนผู้ซื้อ + engine ไม่สร้างออเดอร์ให้ร้านนั้นอีก (**TC-077** + e2e API ที่รัน engine จริงหลังระงับ)
- [x] ปลดระงับ → subscription กลับมา active เอง โดยรอบถัดไปไม่ย้อนหลัง (≥ พรุ่งนี้) — กฎเดียวกับปุ่ม "กลับมาใช้งาน" ของผู้ซื้อ
- [x] Run engine + time-travel จากหน้า admin ได้ · กดซ้ำวันเดิมออเดอร์ไม่งอกเพิ่ม (**TC-079**)
- [x] ตัวเลขเงินบน dashboard มี DemoBadge

## ข้อมูลที่เกี่ยวข้อง

`profiles.is_admin` + ฟังก์ชัน `is_admin()` + admin policies (migration `..._security_hardening` §4), RPC `admin_stats()` (migration `..._secure_read_apis`), RPC `admin_set_shop_suspension` / `admin_set_product_suspension`, คอลัมน์ `shops.suspended_at` / `products.suspended_at`

## Out of scope

- UI สร้าง/ถอด admin, audit log ของ admin ([ยอมรับความเสี่ยง A-3](../../docs/security-design.md)), แบน user รายคน, ระบบรายงานจากผู้ใช้ (report)
- **ปุ่ม "reset demo data" ในหน้า engine** — ตัดออกโดยตั้งใจ: endpoint ที่ลบข้อมูลทั้งชุดได้จากหน้าเว็บคือความเสี่ยงที่ไม่คุ้มกับความสะดวก (กดผิดครั้งเดียวตอนซ้อมก็หมด) · ใช้ `cd anan-api && npm run db:seed` ซึ่งทำงานเหมือนกันทุกอย่างแต่ต้องตั้งใจพิมพ์
- admin **ดูเคสปัญหาได้แต่ไม่ตัดสินข้อพิพาท** — การปิดเคสยังเป็นงานของร้าน ([feature 16](16-delivery-confirmation.md))
- **"ดูในนามร้านอื่น" (impersonation)** — ผู้ดูแลสลับเข้าโหมดร้านได้ก็จริง (เพิ่ม 2026-08-22) แต่เป็นการเข้า **ร้านของตัวเอง** เท่านั้น ไม่ใช่ทางลัดเข้าไปดูหลังร้านของคนอื่น
  การเปิดให้ผู้ดูแลสวมสิทธิ์ร้านใดก็ได้ต้องมาพร้อม audit log ที่บันทึกว่าใครเข้าดูร้านไหนตอนไหน (ตอนนี้ยังไม่มี — [A-3](../../docs/security-design.md)) และเปิดให้ผู้ดูแลเห็นข้อมูลผู้ซื้อของร้านอื่นซึ่งขัดกับหลัก "ร้านเห็นข้อมูลผู้ซื้อเท่าที่ต้องส่งของ" · ทำเมื่อถูกสั่งและเมื่อมี audit log แล้วเท่านั้น
