# W10 — Admin ดูแลแพลตฟอร์ม

> Actor: Admin | Features: [14-admin](../planing/14-admin.md)
> **ทำจริงแล้ว 2026-08-19 (Phase 6)** — ยกเว้นปุ่ม reset demo ที่ตัดออก (ดู Out of scope ของ feature 14)

## Precondition
- บัญชีถูกตั้งสิทธิ์ผ่าน seed/SQL เท่านั้น: `update users set is_admin = true where email = '...';` (seed มี `admin.demo@anan.local` ให้แล้ว) — **ไม่มี endpoint ไหนสร้าง admin ได้**

## Trigger
- Admin ล็อกอิน → เห็นเมนู "Admin" ในโปรไฟล์ → เข้า `(admin)/`

## Main Flow A: ตรวจภาพรวม

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | เปิด `(admin)/index` | `GET /admin/stats` — `@Roles('admin')` ที่ระดับ controller ปฏิเสธคนอื่นด้วย 403 ก่อนถึง service |
| 2 | Admin | เห็น 9 ตัวเลข + engine runs ล่าสุด 5 รอบ | ผู้ใช้/ร้าน (+ที่ถูกระงับ)/สินค้า/subscription active/ออเดอร์วันนี้/MRR (DEMO)/ยกเลิกเดือนนี้/เคสปัญหาค้าง |

## Main Flow B: จัดการหมวดสินค้า

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | เพิ่มหมวด "อาหารเสริม" + ไอคอน + ลำดับ | `POST /admin/categories` |
| 2 | ระบบ | หมวดโผล่ฝั่ง buyer ทันที | catalog โหลด categories ใหม่ |
| 3 | Admin | ลบหมวดที่มีสินค้า | **FK restrict บล็อก** (P2003) → 409 "ยังมีสินค้า n ชิ้นในหมวดนี้ — ย้ายสินค้าออกก่อนจึงจะลบได้" |

## Main Flow C: ระงับร้าน (moderation)

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | ค้นชื่อร้าน → กด "ระงับ" | confirm: "สินค้าทั้งร้านจะหายจาก catalog **และ subscription ทั้งหมดของร้านจะถูกหยุดชั่วคราว ไม่มีการตัดเงิน** — ผู้ซื้อได้รับแจ้งเตือน" |
| 2 | ระบบ | ยืนยัน | `POST /admin/shops/:id/suspension` — ทรานแซกชันเดียว: `shops.suspended_at` → `subscriptions` ที่ยัง `active` ของร้านนั้นเป็น `paused` + `paused_reason='shop_suspended'` → event `paused` → notification ผู้ซื้อ → คืนจำนวนที่กระทบ |
| 3 | ระบบ | ผลทันที | สินค้าหายจาก catalog เพราะ `VISIBLE_PRODUCT` กรองร้านที่ถูกระงับออก; engine ไม่สร้างออเดอร์ให้ร้านนี้อีก (`BILLABLE_PRODUCT` ใน `dueSubscriptions()`); ร้านเปิดโหมด seller ได้แต่เห็นป้าย "ถูกระงับ" และแก้อะไรไม่ได้ (`requireOperableShop`) |
| 4 | Admin | กด "คืนสถานะ" ภายหลังได้ | `{ suspend: false }` → subscription ที่ถูกแช่แข็งกลับเป็น `active` อัตโนมัติ, `next_order_date = max(เดิม, พรุ่งนี้)` (ขยับหมุดตามเมื่อวันรอบถูกเลื่อน) + แจ้งผู้ซื้อ |

## Main Flow D: ควบคุม Engine (ใช้ตอนเดโม่ — [W09](w09-demo-script.md))

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | `(admin)/engine` → ใส่ run_date (หรือเว้นว่าง = วันนี้) → Run | `POST /admin/engine/run` → ต้องเป็น admin **และ** `DEMO_MODE=true` **และ** NODE_ENV อยู่ใน allowlist จึงจะระบุวันจำลองได้ |
| 2 | ระบบ | แสดงผลลัพธ์ | แถวใหม่ใน `engine_runs`: orders_created, notifications_created |
| 3 | Admin | (ก่อนซ้อมใหม่) คืนข้อมูลเดโม่ | `cd anan-api && npm run db:seed` — ตัดปุ่มในหน้าเว็บออกโดยตั้งใจ (endpoint ที่ล้างข้อมูลทั้งชุดได้จากหน้าจอเสี่ยงเกินกว่าที่ควรมี) |

## Main Flow E: เปิดโหมด DEV ของอีเมล (เพิ่ม 2026-08-22)

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | `(admin)/settings` → เปิดสวิตช์ "เปลี่ยนเส้นทางอีเมล" → กรอกปลายทาง (+ Cc ถ้าต้องการ) → บันทึก | `PUT /admin/mail-settings` — **ตรวจ `MAIL_UAT_MODE_AVAILABLE` + `NODE_ENV` ที่ service** ก่อนเขียน |
| 2 | ระบบ | เขียน `mail_settings` + `audit_logs` ในทรานแซกชันเดียว | CHECK ที่ DB กันไม่ให้ "เปิดโหมดแต่ไม่มีปลายทาง" เกิดขึ้นได้ |
| 3 | ระบบ | หน้าจอขึ้นแถบเตือนว่าโหมดกำลังทำงาน พร้อมปลายทางปัจจุบัน | มีผลกับอีเมลฉบับถัดไปทันที ไม่ต้องรีสตาร์ต API |
| 4 | ใครก็ได้ | กด "ลืมรหัสผ่าน" ตามปกติ | `MailService.send()` เปลี่ยนผู้รับเป็นปลายทางที่ตั้งไว้ + ใส่แถบบอกผู้รับตัวจริงในเนื้อเมล และหัวเรื่องขึ้นต้นด้วย `[DEV → …]` |
| 5 | Admin | `(admin)/logs` แท็บ "อีเมลที่ส่งออก" | เห็นทั้ง **ผู้รับตัวจริง** และ **ที่ส่งไปจริง** พร้อมสถานะ (sent / failed / skipped) |
| 6 | Admin | ปิดสวิตช์เมื่อทดสอบเสร็จ | ปลายทางถูกล้างทิ้งด้วย — ค่าที่ค้างไว้คือกับดักรอวันที่มีคนกดเปิดอีกครั้ง |

## Main Flow F: ตรวจ log ระบบ (เพิ่ม 2026-08-22)

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | `(admin)/logs` แท็บ "การกระทำในระบบ" | `GET /admin/logs/audit` — 50 แถว/หน้า เรียงใหม่สุดก่อน |
| 2 | Admin | กดชิปกรองตามชนิดเหตุการณ์ | ส่ง `?action=` ไปกรองที่ DB (ไม่ใช่กรองในหน้าจอ) |
| 3 | Admin | อ่านแถว | `summary` เป็นข้อความไทยที่สรุปไว้ตั้งแต่ตอนเขียน — **อ่านออกแม้ของที่ถูกอ้างถึงจะถูกลบไปแล้ว** |
| 4 | — | (ไม่มีขั้นตอนลบ) | **ไม่มี endpoint แก้หรือลบ log** — log ที่ผู้ถูกตรวจสอบลบได้ไม่ใช่ log |

## Alternate / Error Flows

- **E1 บัญชีธรรมดาพิมพ์ URL `(admin)/` ตรงๆ:** guard พากลับหน้าผู้ซื้อทันที — ต่อให้ข้าม UI ไปได้ ทุก endpoint ก็ตอบ 403 (ทดสอบทั้งสองชั้นใน TC-075)
- **E2 admin ระงับร้านตัวเอง:** ทำได้ (ไม่มีกฎห้าม) — confirm dialog เตือนเหมือนร้านอื่น
- **E4 เครื่องไม่อนุญาตให้เปิดโหมด DEV (Flow E ขั้น 1):** สวิตช์บนหน้าจอถูกล็อกพร้อมข้อความบอกว่าต้องตั้ง `MAIL_UAT_MODE_AVAILABLE=true` · และถ้ายิง `PUT` ตรงข้ามหน้าจอจะได้ **403 `UAT_MODE_UNAVAILABLE`** — ด่านอยู่ที่ service ไม่ใช่ที่ปุ่ม
- **E5 เปิดโหมดโดยไม่กรอกปลายทาง:** 400 จาก DTO และถึงเล็ดลอดไปได้ CHECK `mail_settings_redirect_needs_target` ที่ DB ก็ปฏิเสธอีกชั้น (สภาพ "เปิดโหมดแต่เมลหายเงียบ ๆ" ต้องเป็นไปไม่ได้)
- **E6 แนบชื่อผู้ใช้/รหัสผ่าน SMTP มากับ body:** 400 จาก `forbidNonWhitelisted` — credential อยู่ `.env` เท่านั้น ไม่มีคอลัมน์ใน DB ให้เก็บด้วยซ้ำ
- **E3 เรียก `POST /admin/engine/run` โดย non-admin:** `RolesGuard` ปฏิเสธด้วย 403 ก่อนถึง service · และถึงเป็น admin จริง การระบุวันจำลองก็ยังต้องผ่านด่าน `DEMO_MODE` อีกชั้น (fail closed)

## Postcondition
- แพลตฟอร์มมีผู้ดูแลครบวงจร: เห็นภาพรวม จัดหมวด คุมคุณภาพร้าน ควบคุม engine ตั้งค่าเมล และตรวจ log ได้จากที่เดียว — ไม่ต้องพึ่ง dev build
- **ทุกการกระทำของผู้ดูแลมีร่องรอยใน `audit_logs`** และอีเมลทุกฉบับที่ระบบส่งมีแถวใน `email_logs` (ปิดความเสี่ยง A-3)
