# W13 — คูปองส่วนลดรายรอบ 2 ระดับ (แพลตฟอร์ม + ร้านค้า)

> Actor: Admin + Seller + Buyer + System | Features: [18](../planing/18-coupons.md)
> เพิ่ม 2026-08-24 · **ทำจริงแล้ว 2026-08-24 (Phase 8)** — flow นี้แทรกเข้าไปใน [W06](w06-recurring-cycle.md) ตรงจังหวะ "engine สร้างออเดอร์" และเพิ่ม action ที่ 8 ให้ [W05](w05-manage-subscription.md)

## Precondition
- มีคูปองที่ admin ออกไว้และยังเปิดอยู่ ([Flow A](#flow-a-admin-ออกคูปอง))
- ร้านออกคูปองของตัวเอง ([Flow A2](#flow-a2-ร้านออกคูปองของตัวเอง-ระดับร้าน)) และ/หรือ ติ๊กสินค้าเข้าร่วมแคมเปญของแพลตฟอร์ม ([Flow B](#flow-b-ร้านตั้งนโยบาย--เลือกสินค้าที่เข้าร่วม))
- ผู้ซื้อมี subscription สถานะ `active` ที่ `next_order_date` ยังอยู่ในอนาคต

## Trigger
ผู้ซื้อเปิดหน้า "ของฉัน" แล้วเห็นปุ่ม "ใช้คูปองกับรอบถัดไป" — หรือได้แจ้งเตือน T-3 ที่บอกว่ารอบนี้มีคูปองใช้ได้

---

## ★ 2 ระดับ ซ้อนกันได้ระดับละ 1 ใบต่อรอบ ★

| ระดับ | ใครออก | ครอบสินค้าไหน | ผู้ซื้อเห็นที่ไหน |
|---|---|---|---|
| `platform` | ผู้ดูแล | สินค้าที่ **ร้านกดเข้าร่วม** รายชิ้น (`coupon_products`) | ช่อง "คูปองแพลตฟอร์ม" |
| `shop` | ร้านค้า | ทั้งร้าน (`applies_to_all_products`) หรือสินค้าที่ร้านเลือก | ช่อง "คูปองร้านค้า" |

**ด่านสุดท้ายอยู่ที่สินค้า** — `products.coupon_policy` (both / platform_only / shop_only / none)
ร้านตั้งเองรายชิ้นเพื่อกันไม่ให้สินค้ากำไรบางถูกลดซ้อนสองชั้น **โดยไม่ต้องถอนออกจากแคมเปญทั้งใบ**

**สูตรเมื่อซ้อน: คิดจากยอดเต็มทั้งคู่แล้วรวม** — ยอด ฿255 · แพลตฟอร์ม 20% (฿51) + ร้าน 10% (฿25.50)
= ลดรวม ฿76.50 → จ่าย ฿178.50 · ถ้ารวมเกินยอด **หนีบที่ใบของร้าน** เพื่อให้สองใบรวมกัน
เท่ากับ `orders.discount_amount` เป๊ะ (ไม่งั้นใบเสร็จบวกไม่ลง)

## Flow A: Admin ออกคูปอง (ระดับแพลตฟอร์ม)

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Admin | คอนโซลผู้ดูแล → หน้า "คูปอง" → "ออกคูปองใหม่" | โหลดฟอร์มเปล่า |
| 2 | Admin | กรอก code · ชื่อ · percent/fixed · มูลค่า · เพดาน · ยอดขั้นต่ำ · ช่วงเวลา · โควตา | ตรวจสด: percent > 100 ไม่ได้ · fixed ใส่เพดานไม่ได้ · `ends_at` ต้องหลัง `starts_at` |
| 3 | Admin | ยืนยัน | `POST /admin/coupons` — **ทรานแซกชันเดียว**: insert `coupons` (`in_use_count = 0`) → insert `audit_logs` (`coupon_created`, `actor_id` จาก token) |
| 4 | ระบบ | — | คูปองโผล่ในรายการของทุกร้านทันที (ยังไม่มีสินค้าไหนเข้าร่วม = ผู้ซื้อยังไม่เห็น) |

**ปิดคูปอง:** `POST /admin/coupons/:id/deactivate` → `is_active = false` + audit · **ไม่มี endpoint ลบ** เพราะใบที่ถูกใช้ไปแล้วต้องอ้างอิงกลับได้ตลอด · ใบที่มีคนจองค้างยังใช้ได้ตามที่จอง

## Flow A2: ร้านออกคูปองของตัวเอง (ระดับร้าน)

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Seller | คอนโซลร้าน → "คูปองของร้าน" → กรอกโค้ด/มูลค่า/ช่วงเวลา/โควตา | ตรวจสด: percent > 100 ไม่ได้ · fixed ใส่เพดานไม่ได้ |
| 2 | Seller | เลือกขอบเขต: **ทั้งร้าน** (รวมสินค้าที่เพิ่มทีหลัง) หรือ **เลือกสินค้าเอง** | โหมดหลังตรวจว่าเป็นสินค้าของร้านผู้เรียกทุกชิ้น (นับเทียบจำนวน ไม่เชื่อ id) |
| 3 | Seller | ยืนยัน | `POST /seller/coupons` — insert `coupons` โดย **service เขียน `tier: 'shop'` + `shop_id` ตายตัว** ไม่รับจาก body |

> **★ ร้านออกคูปองระดับแพลตฟอร์มไม่ได้ ★** `tier`/`shopId` ไม่มีใน DTO เลย —
> แนบมาก็ได้ 400 จาก `forbidNonWhitelisted` · ถ้ารับจาก body ร้านจะประกาศแคมเปญกลางได้ด้วย curl บรรทัดเดียว
> · ร้านที่ผู้ดูแลระงับ **ออก/แก้/ปิดคูปองไม่ได้** (อ่านได้อย่างเดียว)

## Flow B: ร้านตั้งนโยบาย + เลือกสินค้าที่เข้าร่วม

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Seller | หน้าแก้สินค้า → ส่วน "คูปองที่ร่วมรายการ" | `GET /seller/products/:id/coupons` — คูปองที่เปิดอยู่ **แยกเป็น 2 กลุ่มตามระดับ** + เงื่อนไข + บรรทัด "สินค้านี้จะถูกลดสูงสุด ฿X ต่อรอบ" คำนวณจากราคาแผนของสินค้านั้น |
| 2 | Seller | เลือกนโยบายของสินค้าชิ้นนี้ + ติ๊กคูปองที่ครอบ แล้วบันทึกครั้งเดียว | `PUT /seller/products/:id/coupons` body `{ couponIds, couponPolicy }` — **แทนที่ทั้งชุดในทรานแซกชันเดียว** (idempotent) · คูปองที่เลือกได้ต้องเป็นของแพลตฟอร์มหรือของร้านตัวเองเท่านั้น · ownership เช็คที่ service: `product.shop.ownerId = ผู้เรียก` |
| 3 | ระบบ | — | ผู้ซื้อที่ subscribe สินค้านั้นเห็นคูปองในรายการที่ใช้ได้ตั้งแต่รอบถัดไป |

> **ร้านติ๊กออกทีหลังไม่กระทบใบที่ผู้ซื้อจองไปแล้ว** — การจองถือ snapshot ของเงื่อนไขไว้แล้ว การถอนมีผลกับการจองครั้งถัดไปเท่านั้น

## Flow C: ผู้ซื้อจองคูปองกับรอบถัดไป ⭐ main flow

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | Buyer | แท็บ "ของฉัน" → การ์ดกาแฟ → "ใช้คูปองกับรอบถัดไป" | `GET /subscriptions/:id/coupons` — คืนเฉพาะคูปองที่ผ่านทุกด่าน (สินค้าเข้าร่วม · อยู่ในช่วงเวลา · โควตาเหลือ · ผู้ซื้อยังไม่เคยใช้ · ยอดถึงขั้นต่ำ) พร้อม **`discountAmount` ที่คำนวณจาก server** · ใบที่ไม่ผ่านส่งกลับมาแบบเทาไว้พร้อมเหตุผล |
| 2 | Buyer | เลือกใบหนึ่งของแต่ละระดับ → ยืนยัน (**ระดับมาจากตัวคูปอง ไม่ใช่จากค่าที่ client ส่ง**) | `POST /subscriptions/:id/coupon` body `{ couponId }` — **ทรานแซกชันเดียว**:<br>① `coupons.updateMany` เงื่อนไขโควตาอยู่ใน `where` + `in_use_count: { increment: 1 }` → count 0 = `COUPON_EXHAUSTED`<br>② insert `coupon_redemptions` (`status = 'reserved'`, `cycle_date = next_order_date`, snapshot เงื่อนไข + ยอดประมาณการ)<br>③ insert `subscription_events` (`coupon_applied`) |
| 3 | ระบบ | — | การ์ดอัปเดตทันที: "คูปอง NEWROUND20 + BEAN10 · รอบนี้ลด ฿76.50 → ตัดเงินจำลอง ฿178.50" + toast |
| 4 | ระบบ | T-3 ก่อนรอบ | แจ้งเตือน `upcoming_cycle` บอก **ยอดหลังลด** ไม่ใช่ยอดเต็ม |

**ยกเลิกการจองเอง:** `DELETE /subscriptions/:id/coupon/:tier` → เฉพาะระดับนั้น `status = 'released'` + `in_use_count` −1 + event `coupon_released` (ไม่ต้องแจ้งเตือน — ผู้ซื้อกดเอง)

**รอบแรกตอน checkout:** `GET /catalog/plans/:id/coupons?quantity=` แล้วส่ง `couponIds[]` (สูงสุด 2 ใบ ระดับละ 1) ไปกับ `POST /subscriptions` — ทั้งการจองและการใช้เกิดในทรานแซกชันเดียวกับที่สร้าง subscription (`reserved` → `consumed` ทันทีเพราะออเดอร์เกิดเลย)

## Flow D: engine ใช้คูปองตอนตัดเงิน

| # | ผู้กระทำ | การกระทำ | ระบบทำอะไร |
|---|---|---|---|
| 1 | System | cron 01:00 (Asia/Bangkok) — `next_order_date <= วันนี้` | โหลด subscription ที่ถึงรอบ พร้อม redemption ที่ `status = 'reserved'` และ `cycle_date` ตรงกับรอบนั้น |
| 2 | System | **คำนวณส่วนลดใหม่ทั้งสองระดับ** จาก snapshot ของ *เงื่อนไข* | `gross = price_per_cycle × quantity` → คิดแต่ละใบจาก `gross` → `combineDiscounts()` รวมและหนีบ<br>**ไม่ใช้ยอดที่จองไว้ตรง ๆ** เพราะราคาอาจเปลี่ยนไปแล้ว |
| 3 | System | สร้างออเดอร์ — **ทรานแซกชันเดียวต่อ 1 subscription** | insert `orders` (`amount` = ยอดหลังลด · `discount_amount` รวม · `platform_redemption_id` / `shop_redemption_id`) → ตัดเงินผ่าน `PaymentProvider` → insert `payments` → mark ทั้งสองใบเป็น `consumed` พร้อมยอดจริงของแต่ละใบ → เลื่อน `next_order_date` |
| 4 | System | — | แจ้งเตือนผู้ซื้อ + ร้าน ตามปกติของ [W06](w06-recurring-cycle.md) โดยยอดที่แสดงคือยอดหลังลด |

> **รันซ้ำวันเดิมไม่ต้องกันอะไรเพิ่มเลย** — ทั้งก้อนชน `orders UNIQUE (subscription_id, cycle_date)` แล้ว rollback ทั้งทรานแซกชัน คูปองจึงไม่ถูก consume ซ้ำ (idempotency ของ engine ครอบคูปองให้อยู่แล้ว)

## Flow E: คูปองถูกคืน

**กฎเดียว: อะไรก็ตามที่ทำให้ `next_order_date` เปลี่ยนโดยไม่เกิดออเดอร์ → คืนคูปอง** — เขียนอยู่ใน `commit()` ของ `SubscriptionsService` จุดเดียว ทำให้ทุก action ได้พฤติกรรมนี้เหมือนกันหมดโดยไม่ต้องไล่เขียนทีละอัน

| ต้นเหตุ | ระบบทำอะไร | แจ้งผู้ซื้อไหม |
|---|---|---|
| Skip / เลื่อนวันส่ง / เปลี่ยนรอบส่ง / Pause / Cancel | `redemption.status = 'released'` + `in_use_count` −1 + event `coupon_released` ใน **tx เดียวกับ action นั้น** — เขียนอยู่ใน `SubscriptionsService.commit()` จุดเดียว (`keepCoupons: true` เป็นข้อยกเว้นของ "เปลี่ยนที่อยู่" อย่างเดียว) | ไม่ (ผู้ซื้อกดเอง — บอกใน toast พอ) |
| Admin ระงับร้าน/สินค้า → subscription ถูกแช่แข็ง | เหมือนกัน + `released_reason = 'shop_suspended'` | **แจ้ง** — notification `coupon_released` |
| ตอนตัดเงินคำนวณใหม่แล้ว `min_order_amount` ไม่ผ่าน (ร้านลดราคาลง) | คืนคูปอง แล้วตัดเงินยอดเต็ม — **ไม่ consume ที่ 0 บาท** | **แจ้ง** |

## Alternate / Error Flows

- **A1 ผู้ซื้อไม่มีคูปองที่ใช้ได้เลย:** ปุ่มยังอยู่แต่ sheet ขึ้น empty state "ยังไม่มีคูปองสำหรับรายการนี้" — ไม่ซ่อนปุ่ม เพราะผู้ซื้อต้องรู้ว่าฟีเจอร์นี้มีอยู่
- **E1 จองใบที่ 2 ของ *ระดับเดิม* ในรอบเดิม:** partial unique `coupon_one_per_cycle_tier` บล็อก → 409 `COUPON_ALREADY_APPLIED` (ถอนใบเดิมก่อนถ้าจะเปลี่ยน) · **คนละระดับในรอบเดียวกันคือการซ้อน — อนุญาต**
- **E1b สินค้าปิดระดับนั้นไว้ (`coupon_policy`):** ช่องนั้นเทาบนหน้าจอพร้อมเหตุผล และยิง API ตรงได้ 409 `COUPON_TIER_NOT_ALLOWED`
- **E1c คูปองของร้านอื่น:** ไม่โผล่ในรายการเลย และยิงตรงได้ 404 (ไม่ใช่ 403 — กัน enumeration)
- **E2 ผู้ซื้อคนเดิมเคยใช้คูปองใบนี้แล้ว:** partial unique `coupon_once_per_user` บล็อก → 409 `COUPON_ALREADY_USED` — **ยกเลิก subscription แล้วสมัครใหม่ก็ใช้ซ้ำไม่ได้** (นี่คือเหตุผลที่ต้องเป็น index ไม่ใช่การเช็คในโค้ด)
- **E3 โควตาเต็มพอดีตอนกด:** `updateMany` ได้ count 0 → 409 `COUPON_EXHAUSTED` · **ยิงพร้อมกัน 3 เส้นบนใบสุดท้ายสำเร็จได้ 1 เท่านั้น** เพราะเงื่อนไขอยู่ใน `where` ไม่ใช่ SELECT ก่อนเขียน
- **E4 กดตอนถึงวันตัดรอบแล้ว:** 409 `CYCLE_TOO_CLOSE` — "รอบนี้ใกล้ถึงกำหนดแล้ว ใช้กับรอบถัดไปได้"
- **E5 admin กด "Run now" ระหว่างที่ผู้ซื้อกำลังกดจอง:** guard `nextOrderDate: cycleDate` ใน `where` ทำให้ฝั่งใดฝั่งหนึ่งแพ้แน่นอน — ไม่มีทางได้ทั้งออเดอร์ที่ไม่ลดและคูปองที่ถูกจองค้าง
- **E6 ยิง `POST /subscriptions` พร้อม `discountAmount` ใน body:** 400 จาก `forbidNonWhitelisted` — ยอดทุกตัวคำนวณที่ service เท่านั้น
- **E7 ผู้ซื้อ A จองคูปองบน subscription ของ B / seller ติ๊กคูปองให้สินค้าร้านอื่น:** 404 (ownership อยู่ใน `where` ของ service ไม่ใช่ `if`)
- **E8 คูปองลด 100%:** `amount = 0` → `DemoPaymentProvider` คืน `paid` ออเดอร์เกิดปกติ (CHECK `orders_amount_range` อนุญาต `>= 0`)

## Postcondition

- ทุกใบจองมีปลายทางที่ชัดเจนเสมอ: `consumed` (เกิดออเดอร์แล้ว) หรือ `released` (คืนโควตาแล้ว) — **ไม่มีใบที่ค้าง `reserved` อยู่กับรอบที่ไม่มีวันเกิด**
- `coupons.in_use_count` เท่ากับจำนวนแถวที่ `status <> 'released'` เสมอ (invariant ชั้น L3)
- **1 รอบมีใบจองที่ยังไม่ถูกคืนได้ไม่เกินระดับละ 1 ใบ** — บังคับด้วย partial unique `coupon_one_per_cycle_tier` ไม่ใช่ด้วยการนับใน service
- ยอดของสองใบรวมกันเท่ากับ `orders.discount_amount` ของออเดอร์นั้นเสมอ (ใบเสร็จจึงบวกลงเสมอ)
- ออเดอร์ทุกใบที่ `discount_amount > 0` ชี้กลับไปยังใบจองได้เสมอ (CHECK `orders_discount_needs_redemption`) → ตรวจสอบย้อนหลังได้ว่าเงินที่หายไปจากยอดเต็มมาจากคูปองใบไหน ใครออก ร้านไหนเข้าร่วม
- ข้อมูลพอสำหรับวิเคราะห์ในเล่ม: `coupon_redemptions` + `subscription_events` ตอบได้ว่า **ผู้ซื้อที่เคยใช้คูปอง churn ต่างจากคนที่ไม่เคยใช้ไหม** (แม้หน้ารายงานจะยังไม่ทำในเฟสนี้)
