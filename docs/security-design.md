## 1. Trust boundary

```
  ไม่ไว้ใจเลย                    │  ไว้ใจ (โค้ดของเราเท่านั้น)
─────────────────────────────────┼──────────────────────────────────
  Expo app (mobile + web)        │  NestJS API
  - โค้ดทุกบรรทัดผู้ใช้อ่าน/แก้ได้    │  - guard, service, Prisma
  - HTTP request ปลอมได้ทั้งหมด    │  - ถือ JWT secret, DB credential
  - localStorage แก้ได้           │  PostgreSQL (localhost, ไม่เปิดสู่ภายนอก)
  - JavaScript ในหน้าเว็บถูกแทรกได้ │
```

> **หมายเหตุที่เพิ่มหลัง Phase 7.2:** บรรทัด "localStorage แก้ได้" เคยเป็นแค่คำอธิบายว่าทำไมห้ามเชื่อค่าจาก client — แต่ตราบใดที่ **refresh token** ถูกเก็บไว้ในนั้น มันไม่ได้แปลว่าแค่ "แก้ได้" เท่านั้น มันแปลว่า **อ่านออกไปได้ด้วย** ซึ่งเป็นคนละเรื่องกันโดยสิ้นเชิง: ค่าที่ถูกแก้ API ปฏิเสธเองอยู่แล้ว แต่ค่าที่ถูกอ่านออกไปคือกุญแจบัญชีที่ใช้ได้จริงอีก 7 วัน · ตอนนี้ฝั่งเว็บไม่มี token อยู่ในที่ที่ JavaScript อ่านได้อีกแล้ว (ดู §5 · A-9)

**ประโยคที่ใช้ในเล่มได้:** "เส้นแบ่งความไว้ใจอยู่ที่ขอบของ API — ทุกอย่างที่อยู่นอกเส้นนี้ถือว่าถูกปลอมได้ ดังนั้นการตรวจสอบสิทธิ์ทุกครั้งต้องเกิดใหม่ที่ฝั่ง server ไม่ว่าฝั่ง client จะตรวจไปแล้วหรือไม่"

**ความต่างจากสถาปัตยกรรมเดิม:** เมื่อใช้ Supabase ผู้ใช้ยิงเข้า PostgREST ได้ตรง ๆ ฐานข้อมูลจึงต้องเป็นด่านเดียว ตอนนี้ **ฐานข้อมูลไม่เปิดสู่ภายนอกเลย** (bind `localhost`) ด่านย้ายมาอยู่ที่ API แต่ **ข้อสมมติเดิมไม่เปลี่ยน: request ทุกอันถือว่าเขียนขึ้นมาเองด้วยมือ**

## 2. ห้าชั้นป้องกัน

```
คำขอจาก client
  │
  ├─ L1 Transport      HTTPS · CORS allowlist · helmet · rate limit
  ├─ L2 Authentication JwtAuthGuard — token จริง ยังไม่หมดอายุ ผู้ใช้ยังมีอยู่
  ├─ L3 Authorization  RolesGuard (seller/admin) + ownership check ใน service
  ├─ L4 Validation     DTO + class-validator + whitelist (ตัด field แปลกปลอม)
  └─ L5 Data integrity CHECK / FK / UNIQUE ใน Postgres — ด่านสุดท้าย
```

แต่ละชั้นสมมติว่าชั้นบนถูกข้ามมาแล้ว

### L1 — Transport
| มาตรการ | ค่า |
|---|---|
| CORS | allowlist เฉพาะ origin ของแอป (`localhost:8081`, โดเมน production) — ห้าม `*` · `credentials: true` ตั้งแต่ refresh token ย้ายไปอยู่ใน cookie (สเปกห้ามใช้คู่กับ `*` อยู่แล้ว) |
| helmet | เปิด default |
| Rate limit | `@nestjs/throttler` — global 120 req/นาที · `/auth/*` **10 req/นาที** ต่อ IP (พอสำหรับคนพิมพ์ผิด ไม่พอสำหรับไล่เดา) · ปิดได้เฉพาะเมื่อ `NODE_ENV=test` เท่านั้น |
| Payload | จำกัด body 1 MB (อัปโหลดรูปไปที่ Cloudinary โดยตรงด้วย signed upload) |

### L2 — Authentication
| เรื่อง | ค่า | เหตุผล |
|---|---|---|
| Password hash | bcrypt cost 12 | ช้าพอที่จะกัน brute force offline |
| Access token | JWT 15 นาที | หลุดแล้วเสียหายจำกัด |
| Refresh token | 7 วัน · **rotate ทุกครั้ง** · เก็บเฉพาะ hash ใน DB | เพิกถอนได้จริง และตรวจจับการใช้ token ซ้ำได้ |
| **ที่เก็บ refresh token ฝั่ง client** | เว็บ: httpOnly cookie · มือถือ: `expo-secure-store` — ไม่มีที่ไหนที่ JavaScript อ่านได้ | แถวข้างบนจำกัดความเสียหาย *หลัง* token หลุด แถวนี้คือชั้นที่กันไม่ให้หลุดตั้งแต่แรก (§5 · A-9) |
| **ตั๋วรีเซ็ตรหัสผ่าน** | 30 นาที · ใช้ได้ครั้งเดียว · เก็บเฉพาะ sha256 · ขอใบใหม่แล้วใบเก่าตายทันที | มันคือ **กุญแจสำรองของบัญชี** ที่เดินทางผ่านช่องทางที่เราคุมไม่ได้ (กล่องเมล) จึงต้องหมดอายุเร็วและมีอยู่ใบเดียวเสมอ (§5 · ลืมรหัสผ่าน) |
| Payload ใน JWT | **`sub` อย่างเดียว** | ห้ามใส่อีเมล/ชื่อ — token อ่านได้ด้วยตาเปล่า · สิทธิ์ก็ไม่ใส่ เพราะอ่านจาก DB ใหม่ทุก request อยู่แล้ว (แถวถัดไป) |
| ผู้ใช้ถูกลบ/ระงับ | `JwtStrategy` อ่าน `isSeller`/`isAdmin` จาก DB ทุก request | แลกด้วย query 1 ครั้งต่อ request เพื่อให้การถอดสิทธิ์มีผลทันที ไม่ต้องรอ token หมดอายุ |
| การหมุน refresh token | เงื่อนไข `revokedAt: null` ต้องอยู่ใน `where` ของคำสั่ง update แล้วนับแถวที่เขียนได้จริง | เช็คด้วย `if` แล้วค่อยเขียนทีหลัง = 2 request ที่ยิงพร้อมกันผ่านทั้งคู่ ได้ 2 session จาก token ใบเดียว และ reuse detection ไม่ทำงานในจังหวะที่สำคัญที่สุด |

### L3 — Authorization (จุดที่พลาดกันบ่อยที่สุด)

**RolesGuard ตอบได้แค่ "เป็น seller ไหม" ไม่ได้ตอบ "เป็นเจ้าของชิ้นนี้ไหม"** — สองคำถามนี้ต้องถามแยกกันเสมอ

```ts
// ❌ ผิด — seller คนไหนก็แก้ออเดอร์ของร้านคนอื่นได้
const order = await prisma.order.findUnique({ where: { id } });

// ✅ ถูก — ความเป็นเจ้าของอยู่ใน query ไม่ใช่ใน if ทีหลัง
const order = await prisma.order.findFirst({
  where: { id, subscription: { plan: { product: { shop: { ownerId: userId } } } } },
});
if (!order) throw new NotFoundException();  // 404 ไม่ใช่ 403 — ไม่บอกว่ามีของชิ้นนี้อยู่จริง
```

กฎ 3 ข้อ:
1. ownership เป็นส่วนหนึ่งของ `where` เสมอ ไม่ใช่การเช็คหลังดึงข้อมูลมาแล้ว
2. ของที่ไม่ใช่ของผู้เรียก ให้ตอบ **404** ไม่ใช่ 403 (403 ยืนยันว่าของชิ้นนั้นมีอยู่)
3. ตรวจสถานะปัจจุบันก่อนเปลี่ยนเสมอ (เช่น cancel ได้เฉพาะ active/paused) → ผิดสถานะตอบ **409**

### L4 — Input validation
```ts
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,              // field ที่ไม่ได้ประกาศใน DTO ถูกตัดทิ้ง
  forbidNonWhitelisted: true,   // ...และตอบ 400 ให้รู้ตัว
  transform: true,
}));
```
**ทำไมสำคัญ:** ถ้าไม่ตัด field แปลกปลอม การส่ง `{"quantity":1,"status":"paid"}` แล้ว spread เข้า Prisma จะเขียนฟิลด์ที่ไม่ได้ตั้งใจ — เป็นช่องเดียวกับ mass assignment

### L5 — Data integrity
CHECK / FK / UNIQUE ทั้งหมด **ยกมาจาก schema เดิมครบ** เพราะเป็นกฎที่ต้องจริงเสมอไม่ว่าโค้ดชั้นบนจะเขียนถูกหรือผิด:
- `orders UNIQUE (subscription_id, cycle_date)` ← idempotency ของ engine
- `payments UNIQUE (order_id)` ← กันตัดเงินซ้ำ
- `subs_state_consistent` ← cancelled ต้องไม่มี next_order_date
- CHECK ความยาว/รูปแบบทุกฟิลด์ที่ผู้ใช้ป้อน

## 3. กฎเฉพาะของโดเมนนี้ (ยกมาจากของเดิมทั้งหมด)

| กฎ | บังคับที่ไหนตอนนี้ |
|---|---|
| **เงินไม่มาจาก client** — ราคาอ่านจาก `product_plans` เสมอ | `SubscriptionsService.create()` · DTO ไม่มี field `amount` |
| **สถานะการจ่ายไม่มาจาก client** | ไม่มี endpoint ไหนรับ `status` ของ payment |
| **ที่อยู่/บัตรต้องเป็นของผู้เรียก** | ตรวจใน service ก่อน insert (เดิมคือช่องโหว่ S-04) |
| **ลำดับสถานะออเดอร์เดินทีละขั้น** | `OrdersService` ตรวจก่อน update |
| **cancelled ถาวร** | service + CHECK ใน DB |
| **ระงับร้าน = หยุดเรียกเก็บเงินทันที** | `AdminService.suspendShop()` แช่แข็ง subscription + engine กรองออก |
| **ขึ้นราคาต้องแจ้งผู้ซื้อ** | `SellerService.updatePlan()` สร้าง notification ให้ทุก subscriber |
| **ร้านเห็นข้อมูลผู้ซื้อเท่าที่ต้องส่งของ** | response DTO ของ seller มีแค่ `address_snapshot` ไม่มี `buyerId` |
| **ห้ามเก็บเลขบัตรเต็ม** | DTO รับเลข 16 หลัก แล้วตัดเหลือ last4 ก่อนถึง service ชั้นเก็บข้อมูล |

## 4. ช่องโหว่ที่ *เคย* เจอในสถาปัตยกรรมเดิม และตำแหน่งใหม่ที่ต้องกัน

รอบก่อนตรวจ Supabase เจอ 15 ข้อ — ส่วนใหญ่เป็นบทเรียนที่ยังใช้ได้ แค่ย้ายชั้น

| เดิม | ตอนนี้ต้องกันที่ไหน |
|---|---|
| S-01 ผู้ใช้ตั้งตัวเองเป็น admin (`update profiles set is_admin`) | DTO ของ `PATCH /me` ต้องไม่มี `isAdmin`/`isSeller` + `whitelist: true` |
| S-02 client insert payment `status: paid` | ไม่มี endpoint ให้เขียน payment เลย |
| S-03 client สร้าง order เอง | order สร้างได้จาก checkout และ engine เท่านั้น |
| S-04 ใช้ address/card ของคนอื่น | ownership check ใน `SubscriptionsService` |
| S-05 ร้านปลดแบนตัวเอง | `suspendedAt` แก้ได้เฉพาะ `AdminService` · DTO ของ seller ไม่มี field นี้ |
| S-06 ร้านแก้ยอดเงินบนออเดอร์ | DTO ของ seller รับแค่ `status`, `trackingNote` |
| S-07 ร้านเห็น subscription ทั้งแถว | response DTO ตัด buyer identifier ออก |
| S-08 ผู้ซื้อปลอม audit event | `subscription_events` เขียนโดย service เท่านั้น |
| S-11 input ไม่มีขอบเขต | DTO validator + CHECK ใน DB (สองชั้น) |
| B-11 กดยืนยันซ้ำ = ตัดเงินซ้ำ | client มี ref guard **และ** API ควรรับ `Idempotency-Key` (Phase 2) |
| B-12 วันที่เพี้ยนเพราะ UTC | ทั้ง API และ client คิดวันด้วย Asia/Bangkok |
| S-14 ฟังก์ชันใหม่หลุดสิทธิ์ให้ anon | ไม่มีแล้ว — ทุก endpoint ปิดโดย default ต้องใส่ `@Public()` ถึงจะเปิด |
| **S-15 ร้านกด `delivered` เองทั้งที่ยังไม่ได้ส่ง** (เพิ่ม Phase 4.5) | `orders.confirmed_at` เขียนได้จาก `POST /orders/:id/confirm` ของผู้ซื้อ**ที่เดียว** — ไม่มี DTO ฝั่งร้านตัวไหนมีฟิลด์นี้ และ engine ที่ปิดออเดอร์อัตโนมัติก็ไม่แตะ · CHECK `orders_confirm_after_ship` + trigger `guard_order_update` กันอีกสองชั้น |
| **S-16 ยกเลิกออเดอร์โดยไม่คืนเงิน** (เพิ่ม Phase 4.5) | ไม่มี endpoint ให้ตั้ง `status='cancelled'` ตรง ๆ — ต้องผ่าน `POST /seller/orders/:id/cancel` ที่คืนเงิน + แจ้งเตือนในทรานแซกชันเดียว · trigger ปฏิเสธการเปลี่ยนสถานะนอกลำดับ |
| **S-17 ปลอมผู้แจ้ง/ผู้ปิดเคสปัญหา** (เพิ่ม Phase 4.5) | `reporter_id` มาจาก token ของผู้ซื้อ · `resolved_by` มาจาก token ของร้าน · ไม่มีทั้งคู่ใน DTO |
| **S-20 ระงับร้านแล้วแพลตฟอร์มยังเก็บเงินให้** (เพิ่ม Phase 6) | การระงับเขียน `shops.suspended_at` **พร้อมกับ** แช่แข็ง subscription ทุกใบของร้านในทรานแซกชันเดียว (`ModerationService.applySuspension`) · engine กรองด้วย `BILLABLE_PRODUCT` อยู่แล้ว จึงไม่มีทั้งออเดอร์และการตัดเงินหลังจากนั้น |
| **S-21 ร้านหรือผู้ซื้อปลดการแช่แข็งเอง** (เพิ่ม Phase 6) | ร้านแก้ `suspended_at` ไม่ได้ (ไม่มีใน DTO ฝั่ง seller + `requireOperableShop`) · ผู้ซื้อ resume ได้เฉพาะ `pausedReason='user'` ส่วน `shop_suspended` ตอบ 409 |
| **S-19 ได้ของโดยไม่ได้จ่าย** (เพิ่ม Phase 5) | ออเดอร์ที่ `payments.status = 'failed'` ถูกกรองออกจากทุกเส้นทางของร้าน (รายการ · `findOne` · `advance` · ตัวนับ dashboard) — ร้านจึงไม่มีทางกดส่งของให้รอบที่ยังไม่ได้เงิน · การเปลี่ยนสถานะการจ่ายทำได้จาก checkout · engine · `retry-payment` เท่านั้น |
| **S-18 รีวิวโดยไม่เคยได้รับของ / ปลอมจำนวนรอบ** (เพิ่ม Phase 4.5) | `upsertReview()` นับ `orders.status='delivered'` เอง และตอบ 422 ถ้าเป็นศูนย์ · `cyclesReceived` ไม่มีใน DTO ขาเข้า |

> **บทเรียนที่ยกมาทั้งดุ้น:** *กฎที่พึ่ง "คนต้องจำ" จะพังในที่สุด* — ใน NestJS แปลว่า **`JwtAuthGuard` ต้องเป็น global guard** แล้วเปิดเป็นรายจุดด้วย `@Public()` ไม่ใช่ใส่ guard ทีละ controller (ลืมเมื่อไหร่คือรูรั่วทันที)

## 5. สิ่งที่ยอมรับความเสี่ยงไว้ (เขียนในเล่มตรง ๆ)

| # | ยอมรับอะไร | เหตุผล | ทางแก้ใน production |
|---|---|---|---|
| A-1 | payment เป็นการจำลอง | กฎเหล็กข้อ 1 ของโปรเจกต์ | gateway จริงที่ยืนยันด้วย webhook + signature |
| A-2 | ไม่มียืนยันอีเมล | ให้กรรมการทดลองสมัครได้เร็ว | ส่งลิงก์ยืนยันก่อนใช้งาน |
| ~~A-3~~ | ~~ไม่มี audit log ของ admin~~ | **แก้แล้ว 2026-08-22** | ตาราง `audit_logs` แบบเขียนอย่างเดียว + หน้า log ในคอนโซลผู้ดูแล — รายละเอียดข้างล่าง |
| A-4 | ไม่มี 2FA | scope | TOTP |
| A-5 | ผู้ใช้ลบบัญชีเองไม่ได้ (PDPA) | scope | endpoint ลบ + anonymize ออเดอร์เก่า |
| A-6 | DB เปิดเฉพาะ localhost — ยังไม่ได้ทำ backup อัตโนมัติ | เครื่องพัฒนา | `pg_dump` ตามกำหนดเวลา + off-site |
| A-7 | `POST /auth/register` บอกได้ว่าอีเมลนั้นมีในระบบแล้ว (409 `EMAIL_TAKEN`) | เมื่อไม่มีการยืนยันอีเมล (A-2) การไม่บอกแปลว่าผู้ใช้สมัครซ้ำแล้วเงียบหาย · **ปิดช่องทาง timing แล้ว** — hash รหัสผ่านก่อนแตะ DB เสมอ ทั้งสองเส้นทางจึงใช้เวลาเท่ากัน เหลือแค่ status code ที่ต่างกัน | ตอบ 200 เหมือนกันทุกกรณีแล้วส่งลิงก์ยืนยันไปทางอีเมลแทน |

### ที่แก้เพิ่มใน Phase 7.2 — ที่เก็บ refresh token (A-9)

**ปัญหาที่แท้จริง:** ชั้น L2 ทำเรื่องอายุ token · การหมุน · การเพิกถอน · การตรวจจับการใช้ซ้ำ ไว้ครบแล้ว แต่ทั้งหมดนั้นตอบคำถามว่า *"ถ้า token หลุดไปแล้วจะจำกัดความเสียหายยังไง"* — ไม่มีชั้นไหนตอบว่า *"token หลุดไปได้ยังไงตั้งแต่แรก"*

บนเว็บคำตอบคือ **XSS ครั้งเดียว**: `localStorage.getItem('anan.refreshToken')` เป็นบรรทัดเดียวที่ให้กุญแจซึ่งใช้ได้จริงอีก 7 วัน และใช้ได้จากเครื่องไหนก็ได้ในโลก — การหมุน token ไม่ช่วยเลย เพราะผู้โจมตีหมุนต่อเองได้ ส่วน reuse detection จะจับได้ก็ต่อเมื่อเจ้าของบังเอิญกลับมาใช้ใบเดิมชนกันพอดี

**ทางแก้: แยกที่เก็บตาม platform เพราะภัยคนละแบบ**

| | ที่เก็บใหม่ | ปิดอะไร | ยังเหลืออะไร |
|---|---|---|---|
| เว็บ | httpOnly cookie (`anan_rt`) `SameSite=Lax` `Path=/api/v1/auth` | JavaScript อ่านค่าไม่ได้ → XSS **ขโมย token ออกนอกเครื่องไม่ได้** | XSS ยังยิง API ในนามผู้ใช้ได้ขณะที่หน้ายังเปิดอยู่ (ปิดไม่ได้ด้วยที่เก็บ ต้องปิดด้วย CSP) |
| มือถือ | `expo-secure-store` → Keychain (iOS) / EncryptedSharedPreferences (Android) | ไฟล์ที่ถูกดึงออกจากเครื่องได้แค่ ciphertext | เครื่องที่ root/jailbreak แล้วและปลดล็อกอยู่ ยังเข้าถึงได้ |
| ทั้งสองฝั่ง | access token อยู่ใน **หน่วยความจำ** เท่านั้น (เหมือนเดิม) | ไม่เคยแตะดิสก์ | อายุ 15 นาที |

**จุดที่ต้องคิดให้ถูก — ใครได้ token ลง response body**

API ต้องรองรับสอง client ที่ต้องการคนละทาง ตัวแยกจึงต้องเป็นสิ่งที่ **ปลอมไม่ได้**:

```
มี header Origin   → เบราว์เซอร์แน่นอน → cookie เท่านั้น · body ไม่มี refreshToken
ไม่มี Origin       → ไม่ใช่เบราว์เซอร์  → body มี refreshToken · ไม่ตั้ง cookie
```

`Origin` เป็น **forbidden header name** ตาม Fetch spec — JavaScript ในหน้าเว็บตั้งเองหรือลบทิ้งไม่ได้ เบราว์เซอร์ใส่ให้เองทุก POST

> **ทางที่ดูง่ายกว่าแต่ผิด:** ให้ client ส่ง header บอกเองว่าเป็น native (เช่น `X-Client: native`) — โค้ด XSS ก็แค่ใส่ header นั้นแล้วขอ token ลง body ไปเก็บ แล้ว httpOnly ทั้งหมดที่ทำมาก็ไม่เหลือความหมาย · **บทเรียน: ตัวแยกที่ตัดสินเรื่องความปลอดภัย ห้ามเป็นค่าที่ฝั่งที่ถูกกันเป็นคนกรอกเอง**

**หนี้ที่ตามมาจากการใช้ cookie — CSRF**

cookie ถูกเบราว์เซอร์แนบให้เองอัตโนมัติ ซึ่งเป็นเหตุผลเดียวกับที่ CSRF มีอยู่ · endpoint อื่นของระบบรอดด้วย preflight **โดยบังเอิญ** (ทุกตัวมี `Content-Type: application/json` หรือ `Authorization` ซึ่งบังคับให้เบราว์เซอร์ถาม OPTIONS ก่อน แล้ว CORS ปัดตกให้) แต่ `POST /auth/refresh` ในโหมด cookie **ไม่มีทั้ง body และ header พิเศษ** จึงเป็น simple request ที่ยิงจากฟอร์มในเว็บผู้โจมตีได้ตรง ๆ

กัน 2 ชั้น:
1. `SameSite=Lax` — เบราว์เซอร์ไม่แนบ cookie ไปกับ POST ข้าม site เลย (พอสำหรับตอนนี้ทั้งหมด)
2. `AllowedOriginGuard` — ถ้ามี `Origin` ต้องอยู่ใน CORS allowlist ไม่งั้น 403 · **ชั้นนี้มีไว้เพื่ออนาคต**: วันที่ deploy หน้าจอกับ API คนละโดเมนจริง ๆ ต้องเปลี่ยนเป็น `SameSite=None` แล้วชั้นที่ 1 จะหายไปทั้งชั้น (`REFRESH_COOKIE_SAMESITE` ใน `.env` · `env.ts` กันไม่ให้ตั้ง `none` นอก production เพราะมันบังคับ `Secure` = ต้องเป็น HTTPS)

**สิ่งที่ต้องทำแล้วคนมักลืม**

- **ล้าง cookie ทุกครั้งที่ refresh ล้มเหลว** — httpOnly แปลว่าผู้ใช้ล้างเองไม่ได้ ถ้าไม่ล้างให้ เบราว์เซอร์จะส่งใบที่ตายแล้วกลับมาทุกครั้งที่เปิดแอป → ผู้ใช้ติดวง 401 ถาวรโดยไม่มีทางออก (สำคัญเป็นพิเศษเมื่อการรีเซ็ตรหัสผ่านเพิกถอน token ทุกใบด้วย `revoked_reason='password_reset'`)
- **ล้างของเก่าที่ค้างอยู่** — ผู้ใช้ที่ล็อกอินค้างไว้ก่อนอัปเดตยังมี token ตัวจริงนอนอยู่ใน `localStorage` และมันใช้ได้จริงจนครบ 7 วัน · ถ้าไม่ลบ = ย้ายไป cookie แล้วแต่ทิ้งกุญแจสำรองไว้ที่เดิม (`purgeLegacyRefreshToken()` ทำตอนบูต · ฝั่งมือถือย้ายจาก AsyncStorage เข้า keychain แล้วลบต้นฉบับ)
- **`logout` ต้องยิงเสมอบนเว็บ** — โค้ดเดิมข้ามการเรียก API เมื่อไม่มี token ในมือ ซึ่งบนเว็บคือ *ทุกครั้ง* → หน้าจอออกจากระบบแล้วแต่ session ฝั่ง server ยังไม่ถูกเพิกถอน

**ที่เทสไว้:** `src/common/http/refresh-cookie.spec.ts` (15 เคส unit) · `test/auth.e2e-spec.ts` → describe "refresh token ใน httpOnly cookie" (8 เคส รวม CSRF 403 และเคสที่ยืนยันว่า **ไม่มี** `refreshToken` ใน body) · Playwright TC-100 (ไม่มีอะไรหน้าตาเป็น JWT ใน `localStorage` + `document.cookie` มองไม่เห็น cookie) และ TC-101 (logout แล้วยืนยันที่ DB ว่าใบนั้น `revoked_reason='logout'`)
### ที่เพิ่มใน Phase 7.2 — ลืมรหัสผ่าน (กู้บัญชีด้วยอีเมล)

ทางกู้บัญชีคือ **ทางลัดที่ข้ามรหัสผ่านได้ทั้งเส้น** — ถ้ามันอ่อนกว่าหน้าล็อกอิน ความแข็งแรงของหน้าล็อกอินก็ไม่มีความหมาย ทุกข้อข้างล่างจึงเทียบมาตรฐานเดียวกับ refresh token

| ภัย | สิ่งที่ทำ |
|---|---|
| **คัดรายชื่อสมาชิกจาก *คำตอบ*** (endpoint นี้เป็น public และรับอีเมลตรง ๆ) | ตอบ **204 เสมอ** ไม่ว่าอีเมลจะมีในระบบหรือไม่ · หน้าจอขึ้นข้อความ *เดียวกันเป๊ะ* ("ถ้ามีบัญชีที่ผูกกับ … เราส่งลิงก์ไปให้แล้ว") · **การส่งเมลไม่ถูก `await`** จึงไม่มีเวลาของ SMTP ปนเข้ามา (TC-095 เทียบข้อความจริงบนจอ ไม่ใช่แค่ status) |
| **คัดรายชื่อสมาชิกจาก *เวลา*** | ตรึงเวลาตอบกลับที่ **อย่างน้อย 250ms** ทั้งสองเส้นทาง (`FORGOT_MIN_RESPONSE_MS` วางใน `finally` — เส้นทางที่โยน error ต้องเท่ากันด้วย ไม่งั้นความล้มเหลวกลายเป็นออราเคิลแทน) · **ดูข้อจำกัดข้อ 3 ข้างล่าง — นี่คือการตั้งพื้น ไม่ใช่การทำให้ปริมาณงานเท่ากัน** |
| **DB หลุดแล้วยึดบัญชีใครก็ได้** | เก็บ **sha256** ไม่เก็บตัว token · CHECK `password_reset_tokens_hash_fmt` บังคับ hex 64 ตัว ส่วน token จริงเป็น base64url 43 ตัว → **เขียนของจริงลงคอลัมน์นั้นไม่ผ่านตั้งแต่ระดับ DB** ไม่ใช่แค่มารยาทของ service |
| **ลิงก์เก่าค้างในกล่องเมล** | อายุ 30 นาที + ใช้ได้ครั้งเดียว + **ขอใบใหม่ = ใบเก่าตายทันที** (จึงมีตั๋วที่ใช้ได้อยู่ใบเดียวเสมอต่อบัญชี) · การปิดตั๋วใช้รูปแบบเดียวกับการหมุน refresh token: เงื่อนไข `usedAt: null` อยู่ใน `where` ของคำสั่งเขียนแล้วนับแถวที่เขียนได้จริง — ไม่ใช่ `if` ก่อนหน้า (ไม่งั้น 2 request ที่ยิงพร้อมกันตั้งรหัสได้ทั้งคู่) |
| **คนที่แอบเข้าบัญชีอยู่ยังอยู่ต่อหลังเจ้าของเปลี่ยนรหัส** | ตั้งรหัสใหม่สำเร็จ = **เพิกถอน refresh token ทุกใบ** ในทรานแซกชันเดียวกัน (`revoked_reason = 'password_reset'`) · ถ้าไม่ทำ ผู้บุกรุกอยู่ต่อได้อีก 7 วันเต็ม = การรีเซ็ตไม่มีความหมาย · ใบที่ปิดด้วยเหตุนี้ถูกใช้ซ้ำแล้ว **ไม่** ถือว่ารั่ว (เหมือน `logout` — A-8) ไม่งั้น session ใหม่ที่เพิ่งตั้งรหัสเสร็จจะถูกเตะออกตามไปเอง |
| **บอกผู้โจมตีว่าตั๋วใบไหนเคยมีจริง** | ไม่มีจริง / ใช้ไปแล้ว / หมดอายุ → **`INVALID_RESET_TOKEN` ข้อความเดียวกันทั้งสามกรณี** ทั้งที่ API และที่หน้าจอ (TC-097 เทียบข้อความของสองสาเหตุว่าตรงกัน) |
| **ใช้ระบบเราส่งลิงก์ฟิชชิ่ง** | `ForgotPasswordDto` มีแค่ `email` — **ไม่มี `redirectTo`/`callbackUrl`** ปลายทางประกอบจาก `APP_WEB_URL` ของ API เท่านั้น (มีเทสยิง `redirectTo` มาแล้วต้องได้ 400 จาก `forbidNonWhitelisted`) |
| **เครื่องยิงเมลกวนฟรี** | `@Throttle` 3 ครั้ง/5 นาที/IP — เข้มกว่า `/auth/*` ตัวอื่น (10/นาที) เพราะ endpoint นี้ไม่ได้แค่เดารหัส แต่สั่งให้ระบบ**ส่งของออกไปหาคนอื่น** |
| **ตั๋วที่ตายแล้วนอนค้างในตาราง** | engine ลบทิ้งทุกวันรอบเดียวกับ refresh token ที่หมดอายุ (`purgeExpiredTokens`) |

| **เมลถูกดักอ่านระหว่างทาง** | `requireTLS: true` ที่ transporter — ค่า default ของ nodemailer เมื่อ `secure: false` คือ "อัปเกรดเป็น TLS **ถ้า** เซิร์ฟเวอร์รองรับ" ซึ่งแปลว่ารีเลย์ที่ไม่ประกาศ STARTTLS จะทำให้ลิงก์เดินทางเป็น plaintext เงียบ ๆ · ตั้งค่านี้แล้วมันจะล้มแทนที่จะส่ง |
| **token ไปโผล่ใน log** | `MailService` เช็ค `NODE_ENV` ของตัวเองก่อนพิมพ์ลิงก์ ไม่ฝากด่านไว้กับ `env.ts` อย่างเดียว — ด่านนั้น fail-open ถ้าใครรัน production โดยไม่ตั้ง `NODE_ENV` (ค่า default คือ `development`) · บน production จึงได้แค่ error ที่บอกว่าส่งไม่ได้ พร้อมอีเมลที่ถูก mask |

**เนื้อเมลไม่มี PII เกินอีเมลปลายทาง** — ไม่ใส่ชื่อผู้ใช้ ชื่อร้าน บทบาท หรือยอดเงิน เพราะกล่องเมลอาจไม่ได้อยู่กับเจ้าของแล้ว (นั่นคือสาเหตุที่คนกดลืมรหัสผ่านตั้งแต่แรกในหลายกรณี)

**ข้อจำกัดที่ยอมรับ (เขียนในเล่ม):**

1. **กล่องอีเมลของผู้ใช้ถือว่าปลอดภัย** — ใครยึดกล่องเมลได้ก็ยึดบัญชี ANAN ได้ เป็นข้อจำกัดของการกู้บัญชีด้วยอีเมลทุกระบบ · ทางแก้จริงคือ 2FA ซึ่งอยู่นอกขอบเขต
2. **การตรึงเวลา 250ms เป็น "พื้น" ไม่ใช่ "การทำให้เท่ากัน"** — ต่างจาก `login` ที่เผา bcrypt กับ `DUMMY_HASH` จนสองเส้นทางทำงาน *ปริมาณเท่ากันจริง* · ที่นี่เส้นทาง "มีอีเมล" เขียน DB 2 แถว ถ้าวันไหนมันช้าเกิน 250ms (โหลดสูง / lock / autovacuum) ส่วนต่างจะโผล่กลับมา เพราะเส้นทาง "ไม่มีอีเมล" ยังจบเร็วเท่าเดิม
   **ถ้อยคำที่ถูกต้องสำหรับเล่ม:** "ลดส่วนต่างของเวลาให้ต่ำกว่าเกณฑ์ที่วัดได้จริงผ่านเครือข่ายในสภาพปกติ" ไม่ใช่ "ปิด timing oracle ได้สนิท" · การทำให้เท่ากันจริงต้องเขียน DB ทิ้งเปล่า ๆ ในเส้นทางที่ไม่พบผู้ใช้ ซึ่งแพงและทำให้ข้อมูลสกปรก จึงเลือกไม่ทำ
   ชั้นที่รับน้ำหนักจริงคือ **rate limit 3 ครั้ง/5 นาที/IP** — การจะเฉลี่ย jitter ของเครือข่ายออกได้ต้องเก็บตัวอย่างหลักพันต่ออีเมลหนึ่งใบ ซึ่งเพดานนี้ทำให้เป็นไปไม่ได้ในทางปฏิบัติ · เข้าชุดเดียวกับ **A-7** (register ยังบอกได้ว่าอีเมลมีในระบบผ่าน status code)
3. **token อยู่ใน query string ของ URL** จึงติดอยู่ในประวัติเบราว์เซอร์และ access log ของ web server · เป็นข้อจำกัดร่วมของลิงก์รีเซ็ตทุกเจ้า (ลิงก์ในอีเมลพา state มาได้ทางเดียว) · ที่บรรเทาไว้แล้วคือ อายุ 30 นาที + ใช้ครั้งเดียว + ตายทันทีที่ขอใบใหม่ ทำให้ของที่ค้างอยู่ในประวัติไร้ค่าเกือบทันที · หน้าจอ**ยังไม่**ลบ `?token=` ออกจาก address bar หลังอ่านค่า (ทำได้ด้วย `router.setParams` แต่ต้องระวังให้ทำงานเหมือนกันทั้ง web และ native ตามกฎข้อ 3) — ทำเมื่อถูกสั่ง

**การตั้งค่า:** `SMTP_HOST` + `MAIL_FROM` **บังคับเมื่อ `NODE_ENV=production`** (ตรวจใน `env.ts` ตอนบูต) — บนเครื่องพัฒนาปล่อยว่างได้ ระบบจะพิมพ์ลิงก์ลง log แทน · ทางนั้นเข้าถึงไม่ได้เลยบน production เพราะ log ไม่ใช่ที่ของ token และ "ส่งเมลไม่ออกแบบเงียบ ๆ" แปลว่าผู้ใช้จริงกู้บัญชีไม่ได้โดยไม่มีใครรู้
