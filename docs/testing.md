## 1. ทำไมต้องมี (เขียนในเล่มได้)

ตอนนี้ **API ของเราเป็นด่านเดียวที่เข้าถึงฐานข้อมูลได้** — กฎทุกข้อที่เคยอยู่ใน RLS ย้ายมาอยู่ในโค้ด TypeScript ที่คนเขียนลืมได้ ปุ่มที่ซ่อนในแอปไม่ได้ป้องกันอะไรเลยเพราะใครก็ยิง `curl` ตรงเข้า endpoint ได้

test ชุดนี้จึงไม่ได้ตอบว่า "ฟีเจอร์ทำงานไหม" อย่างเดียว แต่ตอบว่า **"คนที่ไม่ใช่เจ้าของยิงเข้ามาแล้วโดนปฏิเสธจริงไหม"** ซึ่งเป็นคำถามที่การกดทดสอบด้วยมือบนหน้าจอตอบไม่ได้

## 2. สามชั้นการทดสอบ

| ชั้น | เครื่องมือ | ตอบคำถามว่า | อยู่ที่ |
|---|---|---|---|
| **L1 — unit** | Jest | ฟังก์ชันล้วน ๆ คำนวณถูกไหม (cycle math, วันที่ Bangkok, normalize MRR) | `src/**/*.spec.ts` — ตอนนี้มี `src/common/date.spec.ts` (49 เคส) + `src/common/http/refresh-cookie.spec.ts` (15 เคส) |
| **L2 — e2e (หลัก)** | Jest + supertest | ยิง HTTP จริงผ่าน guard → pipe → service → DB จริง แล้วได้ status/ข้อมูลตามที่ตกลงไหม | `test/*.e2e-spec.ts` |
| **L3 — ข้อจำกัดของ DB** | e2e ที่ยิง Prisma ตรง | CHECK/FK/UNIQUE ปฏิเสธข้อมูลเสียจริงไหม แม้ service จะพลาด | `test/db-invariants.e2e-spec.ts` |
| **L4 — เส้นทางผู้ใช้** | Playwright + Chromium | ผู้ใช้กดจนจบเส้นทางบนแอปจริงแล้วได้ผลตามที่ตั้งใจไหม | `e2e/specs/*.spec.ts` |

**L2 คือชั้นหลัก** — ทุก endpoint ต้องมี ไม่มีข้อยกเว้น

**L4 ตอบคนละคำถามกับ L2** — L2 พิสูจน์ว่า "ระบบปฏิเสธสิ่งที่ควรปฏิเสธ" แต่พิสูจน์ไม่ได้ว่า **แอปเรียกระบบถูกวิธี** (บทเรียนใน §5.0) L4 จึงกดผ่าน DOM จริงตั้งแต่หน้า login ถึงหน้าผลลัพธ์ แล้วยืนยันซ้ำที่ฐานข้อมูลเมื่อเป็นเรื่องเงินหรือสิทธิ์

> L4 รันบน **ฐานข้อมูลคนละตัว** (`anan_test`) ที่ถูกล้างและ seed ใหม่ทุกครั้ง — ต่างจาก L1-L3 ที่ใช้ `anan` ร่วมกับงานพัฒนา
> มีด่านกันไว้ 3 ชั้นไม่ให้เผลอชี้ผิดตัว ชั้นสุดท้ายคือล็อกอินผ่าน API จริงแล้วอ่านค่า canary กลับมาเทียบ — รายละเอียดที่ [e2e/README.md](../e2e/README.md)

> e2e รันบน **ฐานข้อมูลจริงบนเครื่อง** (`anan`) ไม่ใช่ mock — เพราะสิ่งที่เราอยากพิสูจน์คือ Prisma query + constraint ของ Postgres ทำงานร่วมกันถูกต้อง ถ้า mock Prisma ทิ้ง เท่ากับทดสอบ mock ไม่ได้ทดสอบระบบ

## 3. มี feature ใหม่ → ต้องเพิ่ม test อะไร (ตารางบังคับ)

**endpoint ใหม่ทุกตัวต้องมีอย่างน้อย 3 เคส** มิฉะนั้นถือว่ายังไม่เสร็จ (CLAUDE.md กฎข้อ 8):

| # | เคส | คาดหวัง |
|---|---|---|
| 1 | เจ้าของเรียก ข้อมูลถูก | 200 / 201 + ข้อมูลถูกต้อง |
| 2 | **คนอื่นเรียกของคนอื่น** | 404 (ไม่ใช่ 403 — 403 แปลว่ายืนยันว่า id นี้มีจริง) |
| 3 | **สถานะผิด** เช่น ยกเลิกไปแล้ว / ข้ามรอบซ้ำ | 409 |

เพิ่มอีกตามชนิดของ endpoint:

| ถ้า endpoint... | ต้องเพิ่มเคส | ไฟล์ |
|---|---|---|
| ไม่ได้ใส่ `@Public()` | เรียกโดยไม่มี token → 401 | ไฟล์ของ feature นั้น |
| รับ body | ส่งฟิลด์แปลกปลอมที่ไม่ได้ประกาศใน DTO → 400 | ไฟล์ของ feature นั้น |
| แตะเงิน | ส่ง `amount` / `price` / `status:'paid'` มากับ body → ต้องถูกตัดทิ้งหรือ 400 **และยอดใน DB ต้องมาจากราคาใน DB** | `test/payment-integrity.e2e-spec.ts` |
| ต้องใช้ role | บัญชีธรรมดาเรียก → 403 | ไฟล์ของ feature นั้น |
| เขียนหลายตาราง | ทำให้ล้มกลางคัน → ต้องไม่มีแถวค้างครึ่ง ๆ | ไฟล์ของ feature นั้น |
| เปลี่ยนสถานะ subscription | สถานะปลายทางถูก + มีแถวใน `subscription_events` | `test/subscriptions.e2e-spec.ts` |
| เป็นของ engine | รันซ้ำวันเดิม → จำนวนออเดอร์ต้องไม่เพิ่ม | `test/engine.e2e-spec.ts` |
| เพิ่มคอลัมน์/ตาราง | CHECK ใหม่ปฏิเสธค่านอกช่วงจริง | `test/db-invariants.e2e-spec.ts` |
| **ตอบต่างกันตามว่าข้อมูลมีจริงไหม** (ลืมรหัสผ่าน, สมัคร) | ยิงด้วยของที่ **ไม่มีจริง** → ต้องได้ status + ข้อความเดียวกับของที่มีจริง **และยืนยันใน DB ว่าไม่มีอะไรถูกสร้าง** | ไฟล์ของ feature นั้น |
| **เพิ่มการกระทำที่มีสิทธิ์สูง** (ระงับ/ปลด, แก้ตั้งค่าระบบ) | มีแถวใน `audit_logs` ในทรานแซกชันเดียวกับการกระทำ · `summary` มีชื่อของสิ่งที่ถูกกระทำ (ไม่ใช่แค่ id) | ไฟล์ของ feature นั้น |
| **เพิ่มสวิตช์ที่กระทบทั้งระบบ** (โหมด DEV, time-travel) | ปิดสวิตช์ที่ env แล้วยิง API ตรง → ต้องถูกปฏิเสธ (ด่านอยู่ที่ service ไม่ใช่ที่หน้าจอ) | ไฟล์ของ feature นั้น |
| **ออก token ที่ใช้ทำอะไรได้** (ตั๋วรีเซ็ต, invite) | ใช้ซ้ำ → ปฏิเสธ · หมดอายุ → ปฏิเสธ · ขอใบใหม่แล้วใบเก่าต้องตาย · DB ต้องเก็บ hash ไม่ใช่ตัว token | ไฟล์ของ feature นั้น |
| **มีหน้าจอให้ผู้ใช้กด** | **เส้นทางสำเร็จอย่างน้อย 1 เคสในชั้น L4** | `e2e/specs/<feature>.spec.ts` — ดู §3.1 |

> **กฎการอัปเดตเอกสาร:** เพิ่ม feature แล้วต้องเพิ่มบรรทัดใน §5 (สารบัญ test) ใน commit เดียวกัน — ไม่ใช่ทำทีหลัง

## 3.1 feature ใหม่ที่มีหน้าจอ → ต้องเพิ่ม test ชั้น L4 ด้วย (ตารางบังคับ)

endpoint ใหม่ที่ไม่มีใครกดถึงไม่ถือว่าเสร็จ — **flow ที่ผู้ใช้กดได้ต้องมีเคส L4 อย่างน้อย 1 เคส** มิฉะนั้นถือว่ายังไม่เสร็จเหมือนกับกฎ 3 เคสของ L2

| ถ้า feature ใหม่... | ต้องเพิ่มใน `e2e/` | ระดับ |
|---|---|---|
| มีหน้าจอ/ปุ่มใหม่ | เพิ่ม prop `id` ที่ component แล้วลงทะเบียนใน `e2e/helpers/selectors.ts` | บังคับ |
| มี flow ที่ผู้ใช้กดจนจบได้ | 1 เคสเส้นทางสำเร็จ | P0/P1 |
| **แตะเงิน** | เคสที่ยืนยัน **ยอดใน DB** ด้วย `queryTestDatabase()` ไม่ใช่แค่ตัวเลขบนจอ | P0 |
| **เปลี่ยนสถานะ** (pause/cancel/ยืนยันรับของ) | เคสที่ยืนยันสถานะปลายทางบนจอ **และ** ในฐานข้อมูล | P0 |
| มีกฎที่ UI ซ่อนปุ่มไว้ | เคสที่เปิด URL ตรงข้าม UI แล้วต้องถูก API ปฏิเสธ (เช่น TC-026) | P0 |
| มีการตรวจข้อมูลในฟอร์ม | 1 เคสกรอกผิดแล้วต้องขึ้น error รายช่อง | P2 |
| เพิ่ม role ใหม่ (seller/admin) | เพิ่ม role นั้นใน `e2e/helpers/test-data.ts` แล้วใช้ `loginAs(page, '<role>')` | บังคับ |

**ขั้นตอนสั้น ๆ ตอนเพิ่มเคส**

1. ใส่ `id` ที่ component/หน้าจอ → ลงทะเบียนใน `helpers/selectors.ts` พร้อมคอมเมนต์ชื่อไฟล์ต้นทาง
2. เขียนเคสด้วย `testCase({ id, priority, feature }, title, fn)` แบ่ง step เป็น Arrange / Act / Assert
3. รหัส TC ต่อจากเลขสุดท้ายที่มีอยู่ — **ห้ามใช้เลขซ้ำแม้เคสเก่าจะถูกลบไปแล้ว** (รายงานในเล่มอ้างเลขนี้)
4. เคสที่เปลี่ยนสภาพร่วม (ที่อยู่หลัก, ชื่อผู้ใช้) ต้องคืนค่าเดิมด้วย `test.afterAll` หรือ step ชื่อ `Cleanup`
5. `cd e2e && npm run test:e2e` ให้เขียว แล้ว commit `e2e/reports/report.md` ไปด้วยในรอบเดียวกัน

## 4. วิธีรัน

```powershell
cd anan-api
npm run check          # typecheck + lint + unit + e2e  ← ก่อนปิดงานทุกครั้ง
npm run test           # unit อย่างเดียว
npm run test:e2e       # e2e อย่างเดียว (รันเรียงลำดับ --runInBand)
npm run db:seed        # คืนข้อมูลเดโม่กลับสภาพเดิม
```

**ชั้น L4 อยู่คนละแพ็กเกจ** (`anan-api` มี script ชื่อ `test:e2e` อยู่แล้วจึงเลี่ยงชื่อชน):

```powershell
cd e2e
npm run test:e2e       # ทั้งชุด — ยก API + Expo web ให้เองแล้วปิดให้ตอนจบ
npm run test:e2e:ui    # โหมด UI ไล่ดูทีละ step
npm run test:e2e -- --grep TC-019
```

ครั้งแรกต้อง `npm install` + `npx playwright install chromium` + `cp .env.example .env` ก่อน

**e2e รันเรียงลำดับเสมอ (`--runInBand`)** เพราะทุกไฟล์ใช้ฐานข้อมูลเดียวกัน — ถ้ารันขนานกันจะแย่งข้อมูลกันจนผลไม่นิ่ง

## 5.1 หมายเหตุสภาพแวดล้อม (Windows)

- **PostgreSQL 17 ติดตั้งบนเครื่อง** (service `postgresql-x64-17`, port 5432) ไม่ใช้ Docker — `psql.exe` อยู่ที่ `C:\Program Files\PostgreSQL\17\bin\` (ไม่อยู่ใน PATH)
- **pgAdmin รันทุกคำสั่งในหน้าต่าง Query Tool เป็น transaction เดียว** — `CREATE DATABASE` จึงพัง (`25001`) ต้องลากเลือกทีละคำสั่งแล้วกด ▶
- **ล็อก Prisma ไว้ที่ v6** — v7 เปลี่ยนไปใช้ `prisma.config.ts` + driver adapter และ generator แบบ ESM ซึ่งยังไม่เข้ากับ build แบบ CommonJS ของ Nest ได้เนียน ๆ (ถ้าจะขยับเวอร์ชันต้องตั้งใจทำ ไม่ใช่ `npm update`)
- **`prisma migrate reset` ลบข้อมูลทั้งฐาน** — Prisma มีตัวกันไม่ให้ AI agent รันเอง ต้องได้รับคำยืนยันจากคนก่อน
- ห้ามใช้ PowerShell `Get-Content`/`Set-Content` กับไฟล์ที่มีภาษาไทย — PowerShell 5.1 อ่านเป็น ANSI แล้วทำข้อความเพี้ยนทั้งไฟล์ (ใช้เครื่องมือแก้ไฟล์โดยตรงแทน)
- path ที่มีวงเล็บเหลี่ยม เช่น `app\(buyer)\product\[id].tsx` ต้องใช้ `-LiteralPath` — ไม่งั้น PowerShell ตีความ `[id]` เป็น wildcard แล้วคำสั่งไปโดนไฟล์ผิดตัว

## 6. ข้อตกลงการเขียน test

- **สร้างแอปด้วย `createTestApp()` จาก `test/utils/app.ts` เท่านั้น** — มันเรียก `configureApp()` ตัวเดียวกับ `main.ts` ทำให้ guard / ValidationPipe / exception filter ครบเหมือนของจริง ถ้าประกอบแอปเองใน test จะกลายเป็นทดสอบระบบคนละตัวกับที่ deploy
- **test ต้องสร้างข้อมูลของตัวเองเสมอ ห้ามพึ่ง seed** — เคยพลาดมาแล้วตอนใช้ `count(*)` ทั้งตาราง พอ seed มีข้อมูลเพิ่ม test ก็ล้มทั้งที่โค้ดถูก นับเฉพาะข้อมูลที่ไฟล์นั้นสร้างเอง
- **ล้างข้อมูลของตัวเองใน `afterAll`** — ใช้ prefix ที่ระบุตัวได้ เช่น อีเมล `e2e-<ชื่อไฟล์>-<n>@test.local` แล้วลบด้วย prefix นั้น
- ตั้งชื่อเคสเป็นประโยคที่อ่านออกในรายงานผล เช่น `'ผู้ซื้อคนอื่นเรียกดู subscription ของเรา → 404'`
- **เจอบั๊ก → เขียน test ที่จับบั๊กนั้นให้แดงก่อน แล้วค่อยแก้โค้ด** ไม่งั้นไม่มีอะไรยืนยันว่าแก้ตรงจุด
- test ที่แตะเงินต้องยืนยัน **ยอดใน DB** ไม่ใช่แค่ status code ที่ตอบกลับ
